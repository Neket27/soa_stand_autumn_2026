# Чек-лист описания API в требованиях и архитектурной постановке

## Когда применять

Применять этот чек-лист, если в системных требованиях, PRD, CR или архитектурной постановке заявлено создание нового API или изменение существующего API. Проверять каждый затронутый метод отдельно. Если документ касается интеграции, но не меняет API, это должно быть явно указано или очевидно следовать из текста.

## Паспорт метода

Для каждого метода должно быть указано:

| Элемент | Что проверить |
|---|---|
| Название метода | Есть человекочитаемое название операции. |
| Краткое описание | Описано, для чего метод нужен и какой бизнес- или системный сценарий закрывает. |
| Метод и URL | Указаны HTTP-метод и полный path, например `POST /coordinator/api/v1/index/fulltext/task/project/{project}/config`. |
| Тип изменения | Понятно, метод новый или меняется существующий контракт. |
| Компонент-владелец | Понятно, какой сервис или компонент реализует метод. |

## Ограничения

Проверить, что ограничения перечислены явно или явно указано их отсутствие:

- максимальное число сущностей в одном запросе;
- максимальный размер тела запроса;
- допустимая частота вызовов и наличие rate limits;
- ожидаемая нагрузка, например не более X запросов в минуту;
- таймауты, SLA/SLO и допустимая задержка ответа;
- ограничения по ролям, контурам, проектам, tenant-ам или типам данных;
- ограничения повторных запросов, ретраев и идемпотентности.

Если численные значения неизвестны, это риск оценки: в замечании указать, какое значение или диапазон нужен для проектирования, тестирования и эксплуатации.

## Описание запроса

Должна быть таблица или эквивалентное описание базовых параметров:

| Параметр | Что проверить |
|---|---|
| URL | Полный path с path-параметрами. |
| Метод | HTTP-метод: `GET`, `POST`, `PUT`, `PATCH`, `DELETE` или другой применимый метод. |
| Content-Type | Формат тела запроса, например `application/json`. |
| Authorization | Требуемая схема авторизации или явное указание, что авторизация не нужна. |

Проверить параметры заголовков запроса:

| Поле | Что проверить |
|---|---|
| Имя параметра | Точное имя header-а. |
| Тип | Тип или формат значения. |
| Обязательность | Обязательный, опциональный или условно обязательный. |
| Описание | Для чего нужен header и как влияет на обработку. |
| Значение | Допустимые значения, пример или ссылка на источник. |

Проверить path/query-параметры, если они есть. Для каждого параметра должны быть указаны имя, тип, обязательность, допустимые значения, ограничения и описание.

Проверить тело запроса. Если тело является JSON-объектом, для каждого элемента должны быть указаны:

| Поле | Что проверить |
|---|---|
| Имя элемента | Точное имя поля JSON. |
| Тип | Тип, формат, вложенная структура, массив или объект. |
| Обязательность | Обязательное, опциональное или условно обязательное поле. |
| Описание | Семантика поля и влияние на алгоритм. |
| Комментарий | Ограничения, default-значения, валидация, совместимость. |

## Пример запроса

Для каждого метода должен быть хотя бы один валидный пример запроса с URL, headers и телом, если тело применимо. Пример должен соответствовать описанной схеме и не содержать секретов, токенов или персональных данных. Если есть важные альтернативные режимы работы, нужны отдельные примеры для этих режимов.

## Описание ответа

Проверить, что описаны выходные параметры и успешные сценарии:

- заголовки ответа с именем, типом, обязательностью, описанием и примером значения;
- HTTP status успешного ответа;
- тело ответа в формате JSON или явное указание, что тело отсутствует;
- для каждого элемента JSON: имя, тип, обязательность, комментарий или описание;
- пример успешного ответа.

## Ошибочные сценарии

Документ должен описывать не только `200/201`, но и негативные сценарии. Проверить таблицу кодов состояния:

| Поле | Что проверить |
|---|---|
| Код | HTTP status, например `400`, `401`, `403`, `404`, `409`, `422`, `429`, `500`, `503`. |
| Текстовое сообщение | Краткое человекочитаемое сообщение. |
| Описание ошибки `message` | Что именно означает ошибка и когда возникает. |
| Примечание | Как клиент должен обработать ошибку, можно ли повторять запрос, есть ли retry-after. |

Также проверить:

- формат тела ошибки и обязательные поля JSON;
- заголовки ошибки, включая `Retry-After`, если есть rate limit;
- ошибки валидации входных параметров;
- ошибки авторизации и доступа;
- ошибки отсутствия сущности или конфликта состояния;
- ошибки зависимых систем, таймауты и частичные сбои;
- поведение при превышении лимитов.

## Алгоритм работы метода

Для каждого метода должен быть описан алгоритм обработки в виде нумерованных шагов. Проверить, что в алгоритме есть:

- проверка авторизации и прав;
- валидация path/query/header/body-параметров;
- проверка существования и состояния доменных сущностей;
- работа с транзакциями, блокировками или другими механизмами согласованности, если меняются данные;
- вызовы зависимых систем и обработка их ошибок;
- формирование успешного ответа;
- формирование ошибок и логирование значимых событий;
- события аудита, мониторинга и метрики, если метод влияет на данные или эксплуатацию.

## Гонки, corner cases и отказные сценарии

Отдельно проверить, что документ учитывает:

- проблему гонок при одновременном создании, изменении или удалении одной сущности;
- выбранное решение гонок: optimistic lock, pessimistic lock, уникальные ключи, идемпотентный ключ, compare-and-set, очередь или другой механизм;
- повторную отправку одного и того же запроса клиентом;
- частичное выполнение операции и компенсацию;
- недоступность зависимых сервисов;
- пустые массивы, отсутствующие необязательные поля, неизвестные enum-значения, слишком длинные строки, дубли в массивах;
- совместимость с существующими клиентами при изменении контракта.

## Классификация замечаний

- `C`: отсутствует метод/URL, request/response-контракт, авторизация для защищенного метода, критичный ошибочный сценарий или решение гонок для мутационного API.
- `L`: неоднозначен алгоритм, статусы, состояние сущностей, идемпотентность, совместимость или обработка конфликтов.
- `D`: не хватает примеров, численных ограничений, rate limits, таблиц header/body/response, описания мониторинга или эксплуатационных параметров.
