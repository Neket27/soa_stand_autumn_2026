# Карта ролей для онбординга (`/guru-start`)

Справочник команды `/guru-start`: что предложить человеку в зависимости от его
производственной роли. Виды работ и распределение по навыкам переведены из
согласованной таблицы GuruFlow в формат «должность → что делать» — карта не
выдумана здесь. Самой таблицы в репозитории нет: она живёт во внутренней
документации тиражирования, и ссылку на файл, которого тут не существует, эта
страница не даёт.

**Как этим пользоваться.** Реальный состав установленного даёт
`scripts/guru_catalog.py`. Показывать пользователю нужно пересечение: пункт карты
живой, только если его навык есть в `skills` каталога. Отсутствующие навыки не
замалчивать — назвать одной строкой вместе с командой установки из `missingCore`.

**Инвариант.** Имена навыков здесь пишутся в обратных кавычках и обязаны
принадлежать реестру `FAMILY` в `scripts/guru_catalog.py` (исключения — список
`_ROLES_NON_FAMILY_ALLOWED` в smoke-сьюте). Это проверяется тестом.

## 1. Менеджер / владелец продукта / тимлид

| Что делает роль | Чем помогает GURU | Одной командой |
|---|---|---|
| Оценивает бэклог | Авто-оценка задачи по историческим данным, роль валидирует | `estimation-service` по описанию задачи |
| Режет эпик CRPV на истории | Декомпозиция по стандарту с INVEST-гейтом | `guru-crpv-decomposer`, гейт — `user-story-invest-analyzer` |
| Держит поток задач | Что назначено, что закрыто за период | `swtr_task_tool.py assigned / done-weekly` |
| Входной контроль постановки | Ревью документа на полноту и противоречия | `pvm-guru`, сценарий 4 |
| Проверяет спорное решение | Аргументы за и против с проверкой по коду | `guru-dialectic` |
| Заводит контекст проекта | Интервью и контекст-пак, из которого читают все навыки | `guru-context` |
| Ведёт фичу на несколько репозиториев | Один план на фичу, разнесение по репозиториям, покрытие требований и порядок архивации | `guru-multirepo` |

**С чего начать команде.** Первый шаг лида — `guru-context`: без контекст-пака
каждый навык угадывает границы, термины и запреты заново. Один раз заполненный
пак читают и `guru-brainstorm`, и `guru-design`, и `exec`.

**Демо:** `swtr_task_tool.py done-weekly` по своей команде или `assigned --me` — read-only, безопасно.

## 2. Аналитик

| Что делает роль | Чем помогает GURU | Одной командой |
|---|---|---|
| Пишет системные требования | Драфт первой версии из собранных источников | `pvm-guru`, сценарий 4 |
| Проверяет готовые СТ | Ревью на полноту, качество, непротиворечивость | `pvm-guru`, сценарий 4 |
| Готовит тестовую модель | Реестр атомарных требований с трассировкой | `prd-requirement-decomposer` → `requirements.csv` |
| Ищет контекст | Похожие задачи и страницы вики по словам | `swtr_task_tool.py search` / `similar` |
| Прорабатывает сырую идею | Вопросы по одному, 2–3 подхода, дизайн по частям | `guru-brainstorm` |
| Заводит изменение по задаче | Заготовка proposal из полей задачи, без выдуманных разделов | `pvm-guru`, сценарий 18 |
| Пишет комментарии и описания | Коротко и по делу, без канцелярита | `guru-writing-style` |

**Цепочка на изменение:** `pvm-guru` (сценарий 18, заготовка) → `guru-brainstorm`
(proposal и требования) → `guru-design` (привязка требований к коду) → `plan`
(задачи). Проверяет артефакты на каждом шаге `guru-openspec`.

**Демо:** ревью реальной задачи пользователя. Отчёт пишется в `docs/ai/<slug>/` — спросить разрешение.

## 3. Архитектор

| Что делает роль | Чем помогает GURU | Одной командой |
|---|---|---|
| Пишет архитектурную постановку | Драфт первой версии | `pvm-guru`, сценарий 4 |
| Проверяет доработанную постановку | Ревью по чек-листам, согласованным между ПАО и СБТ | `pvm-guru`, сценарий 4 |
| Ищет, где это реализовано | Поиск по коду и репозиториям | `source_control_search.py` |
| Сверяет документ с кодом | Сопоставление постановки и реализации | `pvm-guru`, сценарий 8 |
| Защищает архитектурное решение | Тезис, антитезис и сверка вывода с кодом | `guru-dialectic` |
| Прорабатывает подход до постановки | 2–3 варианта с trade-offs и рекомендацией | `guru-brainstorm` |
| Определяет, какие репозитории затронет фича | Разбор с доказательством: затронут, не затронут или неясно — со ссылкой файл:строка, а не по памяти | `guru-multirepo` |

**Кросс-репо поток:** `guru-multirepo` analyze (какие репозитории затронуты) →
decompose (per-repo изменения с `Covers:` на общие требования) → `exec` в каждом
репозитории → verify (полнота покрытия) → archive. Одиночное изменение в одном
репозитории этот навык не ведёт — там обычная цепочка через `plan`.

**Демо:** сопоставить его постановку с кодом — read-only.

## 4. Разработчик

| Что делает роль | Чем помогает GURU | Одной командой |
|---|---|---|
| Разбирается в задаче | Карточка задачи со связями и вики | `swtr_task_tool.py get` |
| Делает задачу | План, затем исполнение задача-за-задачей | `plan` → `exec` |
| Ревьюит PR | Разбор diff, архитектуры, тестов, scope creep | `guru-pr-review` |
| Готовит задачу агенту | Сырой тикет → исполнимая постановка | `agent-task-rewriter` |
| Чинит непонятную поломку | «5 почему» с доказательствами до предложения фикса | `guru-root-cause-investigator` |
| Проектирует изменение | Разведка кода и привязка требований к классам | `guru-design` |
| Создаёт PR | Описание со ссылкой на задачу, проверка дублей | `pvm-guru`, сценарий 19 |
| Пишет комментарий к PR | Коротко, прямо, со ссылками на строки | `guru-writing-style` |

**Цепочка на готовом изменении:** `guru-design` → `plan` (задачи в `tasks.md`) →
`exec` (исполнение с гейтом L1, верификацией L2 и drift) → `pvm-guru` сценарий 19
(создать PR) → `guru-pr-review` (ревью созданного).

**Демо:** `plan` по его назначенной задаче. Файл плана пишется в `docs/plans/` —
спросить разрешение. `exec` в онбординге не запускать: он делает коммиты.

## 5. Тестировщик

| Что делает роль | Чем помогает GURU | Одной командой |
|---|---|---|
| Пишет автотесты | План, затем исполнение | `plan` → `exec` |
| Работает с TMS | Тест-планы, циклы, кейсы, прогоны — read-only | `swtr_task_tool.py tms <kind>` |
| Считает покрытие | Реестр требований как основа тестовой модели | `prd-requirement-decomposer` |
| Разбирается в задаче | Карточка задачи и связанные документы | `swtr_task_tool.py get` |
| Разбирает мигающий тест | «5 почему» вместо «перезапустим ещё раз» | `guru-root-cause-investigator` |

**Демо:** `tms test-plans` по его пространству — read-only.

## 6. Техписатель / документация

| Что делает роль | Чем помогает GURU | Одной командой |
|---|---|---|
| Пишет документ | Proposal по документации на основе задачи и кода | `pvm-guru`, сценарии 2 и 4 |
| Собирает источники | Задача + вики + код в одном месте | `fetch_swtr_sources.py` |
| Документирует Python-сервис | Генерация по шаблонам | `python-docs` (ставится отдельно) |
| Пишет в задачи и PR | Стиль для рабочих комментариев; README и публичные тексты — по обычным правилам | `guru-writing-style` |

**Демо:** собрать источники по его задаче и показать скелет документа.

## 7. Другое / несколько ролей сразу

Свободный ввод. Собрать объединение ближайших разделов и уточнить одним вопросом,
что из этого ближе к его сегодняшней работе. Если роль не опознаётся вовсе —
показать раздел «Разработчик» и раздел «Аналитик» как две самые частые точки входа
и спросить, что откликается.

## Общее для всех ролей

- `/guru_doctor` — доступы к четырём системам; первое, что стоит запускать при любой ошибке авторизации.
- `/guru_profile` — умолчания (логин, пространства, проект SourceControl): собираются в `/guru-start`, правятся этой командой, разово обходятся флагом `--no-profile`.
- `docs/guru-family.md` — как навыки семейства связаны и как передавать данные между ними.
- `references/usage-scenarios.md` — все сценарии навыка `pvm-guru` с примерами команд.
