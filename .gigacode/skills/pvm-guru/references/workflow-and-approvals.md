# Процессы, статусы и согласования SWTR

Модель, которая стоит за сменой статуса и за согласованиями. Механика перехода (какие endpoint-ы
дёргать, как читать отказы, команда `status set`) — `references/task-tracker-operations.md`, раздел
«Смена статуса юнита»; здесь то, что объясняет её поведение.

Источник модели — документация платформы АС-21 (руководство администратора Task Tracker,
REL 33.4.0). Поведение API, отмеченное как проверенное, подтверждено нашими живыми
запросами; всё остальное помечено явно.

## Категория статуса — единственная переносимая семантика

У каждого статуса есть **категория** (в API — `statusType`), и категорий ровно три:

| Код | Название | Смысл |
|---|---|---|
| `pause` | Ожидание | задача заведена или отложена, работа не идёт |
| `progress` | В работе | работа идёт |
| `done` | Завершено | терминальное состояние |

Больше категорий не бывает: справочник закрыт. Категория приходит внутри статуса — и в текущем
состоянии юнита, и в обоих концах перехода:

```text
oldStatus / destStatus / currentStatus:
  code: "NPRGRS_isFIvnhYcKLkj"   ← это значение сравнивает TQL
  name: "In progress"
  statusType:
    code: "progress"             ← категория
    name: "В работе"
```

**Почему это важнее самих статусов.** Имена и коды статусов уникальны для каждой схемы workflow, и
набор их в тенанте разнородный: читаемые (`closed`), кириллические (`в_очереди`) и генерируемые
(`CLSD_YLquKLRWNLxhnnC`). Условие «незакрытые задачи», написанное списком кодов, работает в одном
пространстве и молча возвращает пустоту в другом. Переносимо только через категорию — в TQL это
функция `statusCategory("done"|"progress"|"pause")`, см. `references/tql.md`.

## Инварианты процесса

Процесс («workflow») — формализованное описание этапов выполнения задачи. Что из этого следует
для агента:

1. **Один процесс на пару (тип задачи, пространство).** Двух параллельных схем у одного типа в
   одном пространстве не бывает — если статусы юнита выглядят «из другой схемы», значит процесс
   меняли (см. пункт 6).
2. **Переход — это тройка** «исходный статус → целевой статус + действие». Действие берётся из
   глобального справочника действий тенанта, и именно его имя видит пользователь на кнопке.
   Перехода без действия не существует; поэтому статус меняется выполнением действия, а не записью
   значения.
3. **Бывают переходы «из любого статуса».** У статуса есть флаг, включающий вход в него из всех
   прочих статусов диаграммы одним действием. В обычном перечислении рёбер такой переход выглядит
   иначе, чем набор явных пар: маршрутизатор `status set`, строящий кратчайший путь по графу,
   обязан считаться с тем, что часть переходов задана не парами, а флагом.
4. **Один переход может иметь несколько исходных статусов** — при настройке это разворачивается в
   несколько рёбер с общим действием и общим целевым статусом.
5. **Валидная схема обязана иметь**: начальный статус (в нём создаются задачи), хотя бы один
   статус категории «Ожидание», хотя бы один категории «Завершено», и все статусы достижимыми из
   начального. Поэтому недостижимого статуса в рабочей схеме быть не должно — если маршрут до цели
   не строится, дело в правах и условиях, а не в графе.
6. **Смена процесса переписывает статусы задач.** При замене процесса у типа задачи в пространстве
   конфигуратор обязан сопоставить каждый старый статус новому, причём кандидаты ограничены
   **совместимой категорией**, после чего идёт фоновая миграция всех задач этого типа. Отсюда
   встречаются задачи со статусом, которого «не должно быть» в текущей схеме.
7. **Используемый процесс структурно неизменяем.** Пока по схеме живут задачи, менять её статусы и
   переходы нельзя — только название, описание и раскладку узлов. Значит, наблюдаемый граф
   стабилен, и закешировать его на время сессии безопасно.
8. **Справочники статусов и действий — общие на тенант.** Один и тот же код статуса может
   встречаться в разных процессах; удалить статус или сменить его категорию можно, только если он
   не используется ни в одном процессе.
9. Схемы импортируются и экспортируются как XML в формате **DTD OSWorkflow 2.8** — том же, что у
   Atlassian Jira. Это объясняет Jira-подобную модель: статусы, переходы, действия.

## Discovery: узнать схему до того, как трогать юнит

Наш штатный путь (`status get`) начинается с юнита: он отдаёт текущий статус, доступные действия и
код схемы. Но когда юнита ещё нет — при планировании создания или при вопросе «какие вообще статусы
в этом пространстве» — цепочка другая:

| Шаг | Endpoint | Что отдаёт | Команда навыка |
|---|---|---|---|
| 1 | `POST /rest/api/space/v3/find` (тело `{}`) | список пространств `[{code, name, type}]` | `swtr_task_tool.py spaces` |
| 2 | `GET /rest/api/space/v3/{code}/suits` | типы задач пространства и привязанный workflow | `swtr_task_tool.py suits <space>` |
| 3 | `GET /rest/api/workflow/v1/suit/{suit}/space/{space}/workflow` | схема по паре (тип, пространство): переходы со статусами и категориями | `swtr_task_tool.py workflow --suit … --space …` |
| 4 | `GET /rest/api/suit/v1/{suitCode}` | свойства и атрибуты типа задачи | команды нет |
| 5 | `GET /rest/api/workflow/v1/unit/{code}/status/get?conditionEnabled=true` | состояние конкретного юнита | `status get` |

**Вся цепочка проверена вживую 13.08.2026** и отвечает `200`:

- шаг 1 вернул 85 пространств в форме `{code, name, type:{code,name}, createdAt, updatedAt}`;
- шаг 2 по CRPV показал привязку workflow к каждому типу, причём у `wiki_page` привязка `null` —
  ровно тот случай «тип без процесса», который надо пропускать;
- шаг 3 по паре `epic_crpv` + `CRPV` отдал `{wfSchema, wfSchemaStatuses, wfTransitions}` с 65
  переходами, где у каждого статуса есть `statusType` с кодом категории;
- шаг 4 по типу `task` отдал `baseAttributes` (`summary`, `description`) и полный список
  пользовательских атрибутов с типами и справочными значениями.

Шаги 1, 2, 3 и 5 закрыты командами навыка (колонка справа); у шага 4 команды нет — при
необходимости дёргать вручную.

Шаг 3 отличается от нашего `GET /rest/api/workflow/v1/workflow/{schemaCode}` тем, что не требует
знать код схемы: он адресуется парой «тип задачи + пространство». Именно это делает его пригодным
для планирования до создания юнита.

## Согласования (УМС)

Отдельная подсистема поверх задач. Прямых команд навыка для неё нет — раздел нужен, чтобы агент
правильно **объяснял наблюдаемое** и не выдумывал причин.

### Модель

```text
Согласование (код, привязка к типу задачи)
  └── Этап (код, номер, тип согласующих по умолчанию, максимум участников)
        └── Решение (4 типа; обязательны «Нет решения» и «Положительное»)
              └── Резолюция (текст, код, требуется ли комментарий)
```

Участники бывают двух ролей, и разница принципиальна:

- **Согласующие** — блокируют: пока обязательный согласующий не принял положительное решение, этап
  не завершается;
- **Поручители** — не блокируют: их отсутствующее или отрицательное решение завершению этапа не
  мешает.

Статусы самого согласования: `Ожидание`, `Активный`, `Завершённый`. Пока оно не завершено, решение
можно изменить; в завершённом этапе нельзя ни менять решение, ни добавлять и удалять участников.
Принять решение можно только в тех статусах задачи, для которых оно объявлено доступным.

Правило автозавершения этапа настраивается; типовое значение — «все обязательные приняли
положительное решение».

### Три вещи, которые объясняют «оно само»

1. **Согласование сбрасывается.** Триггеры сброса: переход задачи в заданные статусы, отклонение
   любым согласующим (если включён автосброс) и **изменение значений заданных атрибутов задачи**.
   Последнее — самое неочевидное: правка поля обнуляет собранные голоса.
2. **Согласование меняет статус связанных задач.** При положительном результате настраивается
   кортеж «тип связанной задачи + тип связи + исходный статус → целевой статус», и статус
   переезжает у соседнего юнита. Если пользователь спрашивает, почему задача сменила статус без
   видимого действия, это первая гипотеза — вместе с автопереходами из wiki-УМС.
3. **Правка тела страницы сбрасывает голоса** — для вики-страниц, где УМС включён на завершённом
   этапе; см. `references/wiki-model.md`.

### Терминология: «резолюция» здесь не то же самое, что в Jira

В Jira resolution — поле закрытия задачи. В SWTR «Резолюции» — справочник формулировок к решению
согласующего (с признаком «требуется комментарий»). К закрытию задачи отношения не имеет: за
завершённость отвечает категория статуса `done`.

### Конфигурация (справочно)

Привязка процесса к типу задачи в типе пространства выполняется конфигуратором тенанта:

```http
POST /rest/api/workflow/v1/space/type/suit/list/create
```

```json
{
  "code": "WIKI_TEAM",
  "suit": "wiki_page",
  "workflows": [{"code": "<код процесса>", "default": true}]
}
```

Здесь `code` — код типа пространства, `suit` — код типа задачи, `default` — процесс по умолчанию.
Полномочие на настройку согласований — `approval:write`. Навык этих ручек не вызывает: они
административные, и права конфигуратора тенанта у пользователя навыка, как правило, нет.

Реальные коды из боевой конфигурации согласования вики-страниц: согласование
`wiki_page_validation`, этап `wiki_page_discussion`, решения «Нет решения», «Согласовано»,
«Отклонено».

## Статус проверки

Проверено вживую 13.08.2026: вся discovery-цепочка отвечает `200` (детали выше), `statusCategory()`
в TQL работает и даёт непересекающиеся категории (`references/tql.md`).

Модель согласований (УМС) остаётся знанием из документации: команд навыка для неё нет, отдельных
endpoint-ов мы не дёргали. Она нужна для объяснения наблюдаемого — прежде всего статусов, которые
сменились «сами».
