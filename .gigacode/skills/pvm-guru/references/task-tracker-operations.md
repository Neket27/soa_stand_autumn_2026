# Task Tracker и Wiki операции

## Базовые endpoint-ы

Используемые endpoint-ы SWTR Task Tracker:

- `GET /rest/api/unit/v2/{code}` — получить юнит с атрибутами по коду.
- `POST /rest/api/unit/v3/find` — поиск юнитов через `QLRequestDto` без вычисления полного количества.
- `POST /rest/api/unit/v3/{filter}/find` — поиск внутри быстрого фильтра.
- `POST /rest/api/unit/v3/find/tql` — поиск через TQL.
- `POST /rest/api/unit/v3/count` — количество юнитов по фильтру.
- `POST /rest/api/unit/v3/count/composite` — количество юнитов с поддержкой OR-фильтров и `tqlFilterIds` (используется CLI subcommand `count`).
- `POST /rest/api/unit/v2/{suit}/create` — создать задачу указанного типа.
- `GET /extension/plugin/v2/rest/api/swtr_wiki_plugin/v2/wiki/unit/{unitCode}` — получить wiki-страницу юнита с ссылками.
- `GET /extension/plugin/v2/rest/api/swtr_wiki_plugin/v1/wiki/unit/{unitCode}` — fallback для wiki-страницы.
- `POST /extension/plugin/v2/rest/api/swtr_wiki_plugin/v1/wiki/unit/find` — поиск wiki-страниц.
- Запись вики идёт обычными ручками юнита (`create` и `update` выше), а не плагином: тело страницы —
  атрибут `wiki_page_body`, строкой с JSON ProseMirror внутри. Формат, ловушки и связь с родителем —
  `references/wiki-model.md`, раздел «Запись страницы через API».
- `POST /extension/plugin/v2/rest/api/swtr_task_tracker_plugin/v1/unit/search` — поиск статусов/кодов юнитов по списку кодов.

**Это дефолтный бэкенд навыка.** Любой запрос про задачу или вики без явного указания
системы обрабатывается здесь, а не в Jira/Confluence sberworks — включая голый код
`PVM-…`/`CRPV-…`. См. «Приоритет систем» в `SKILL.md`.

Когда нужен полный нормализованный источник (поле `source` в JSON-выводе, с unit + wiki + извлеченными длинными текстами), использовать:

## Поиск задач по ключевым словам

Высокоуровневый сценарий:

```bash
python3 $SKILL_DIR/scripts/swtr_task_tool.py search 'аудит журналирование миграция' --space PVM --common-attributes --limit 30
```

Что делает скрипт:

1. Ищет юниты через `/rest/api/unit/v3/find`.
2. Использует `properties.or` по `code`, `summary`, `description` с оператором `like`.
3. Если переданы `--attribute-code`, добавляет `filters.attributes.or` с оператором `like`.
4. Если передан `--common-attributes`, пробует распространенные атрибуты: `source`, `business_block`, `solution`, `reporter`, `label`, `component`, `product`, `direction`, `group`, `expected_date` и другие.
5. Параллельно ищет wiki-страницы через `/swtr_wiki_plugin/v1/wiki/unit/find`.

Если Task Tracker возвращает ошибку из-за неизвестного атрибута, повторить команду без `--common-attributes` и передать только точно известные `--attribute-code`.

JSON-вывод `search` содержит `command, query, spaces, suits, attributeCodes, units, wiki`. `units` — сырой ответ `find`, `wiki` — ответ `wiki/unit/find`.

`--space` не задан — область берётся из профиля (`task_tracker.primary_space`, затем `task_tracker.spaces`); что взято, видно в `defaults_applied` и строкой в `notes`. Отключить — `--no-profile`.

## Подсчет задач по фильтру (count / composite)

Когда нужен только счетчик «сколько задач упоминают X» без выгрузки тел задач, использовать subcommand `count`. Под капотом — `POST /rest/api/unit/v3/count/composite` с OR-фильтром по `code`, `summary`, `description` (оператор `like`).

```bash
python3 $SKILL_DIR/scripts/swtr_task_tool.py count "Tarasenkova.O.O" --space PVM
```

Минимальное тело запроса:

```json
{
  "filters": {
    "spaces": ["PVM"],
    "properties": {
      "and": [],
      "or": [
        {"property": "summary", "value": "Tarasenkova.O.O", "operator": "like"},
        {"property": "description", "value": "Tarasenkova.O.O", "operator": "like"},
        {"property": "code", "value": "Tarasenkova.O.O", "operator": "like"}
      ]
    }
  },
  "tqlFilterIds": []
}
```

Опции:

- `--space SPC` — повторяемый. Не задан — пространства профиля, как в разделе про поиск; отключение — `--no-profile`.
- `--suit SUIT` — повторяемый.
- `--extra-or '[{"property":"reporter","operator":"eq","value":"vasiakuzyakin"}]'` — добавить условия в `properties.or`.
- `--extra-and '[{"property":"deleted","operator":"eq","value":false}]'` — добавить условия в `properties.and`.
- `--tql-filter-id ID` — повторяемый, добавляется в массив `tqlFilterIds`.

JSON-вывод: `{command, query, spaces, suits, endpoint, request, matched, response}`. `matched` — извлеченное из ответа число (поля `count`/`total`/`totalCount`/`matched`/`totalElements`/`numberOfElements`); если структура ответа отличается, использовать `response` напрямую.

## Поиск похожих задач

```bash
python3 $SKILL_DIR/scripts/swtr_task_tool.py similar CRPV-35498 --space CRPV --limit 20
```

Алгоритм:

1. Если вход — номер задачи, получить задачу через `/rest/api/unit/v2/{code}`.
2. Извлечь термины из summary, description и атрибутов.
3. Выполнить серию поисков по каждому термину.
4. Схлопнуть дубли по коду юнита.
5. Отсортировать по локальному score: сколько терминов найдено в summary/description/атрибутах.

## Создание задачи

Endpoint: `POST /rest/api/unit/v2/{suit}/create`.

Минимальный JSON тела запроса:

```json
{
  "summary": "Добавить метрики сайзинга для CostCalculator",
  "description": "Нужно добавить метрики LGDB и COTE для снижения погрешности сайзинга.",
  "space": "PVM",
  "attributes": {
    "priority": "mid"
  }
}
```

Dry-run:

```bash
python3 $SKILL_DIR/scripts/swtr_task_tool.py create --suit task --space PVM --summary 'Добавить метрики сайзинга для CostCalculator' --description 'Нужно добавить метрики LGDB и COTE для снижения погрешности сайзинга.' --attribute priority=mid
```

Пропущенные `--suit`, `--space`, `--product` и `--component` подставляются из профиля (`task_tracker.default_suit`, `task_tracker.primary_space`, `task_tracker.product`, `task_tracker.components`); явное значение всегда сильнее. На ветке `--body-file` из профиля берётся только `--suit`: тип стоит в URL (`/rest/api/unit/v2/{suit}/create`), а не в теле, поэтому в само тело не подставляется ничего — ни пространство, ни продукт, ни компоненты. Подстановка видна в `defaults_applied` и в dry-run payload; отключение — `--no-profile`, и тогда тип по умолчанию снова `task`.

Реальное создание:

```bash
python3 $SKILL_DIR/scripts/swtr_task_tool.py create --suit task --space PVM --summary 'Добавить метрики сайзинга для CostCalculator' --description 'Нужно добавить метрики LGDB и COTE для снижения погрешности сайзинга.' --attribute priority=mid --execute
```

Если используются сложные атрибуты, подготовить полный body-файл:

```bash
cat > /tmp/create-body.json <<'JSON'
{
  "summary": "Добавить метрики сайзинга для CostCalculator",
  "description": "Нужно добавить метрики LGDB и COTE для снижения погрешности сайзинга.",
  "space": "PVM",
  "attributes": {
    "workflow_status": {"command": "NEW"},
    "priority": "mid"
  }
}
JSON

python3 $SKILL_DIR/scripts/swtr_task_tool.py create --suit task --body-file /tmp/create-body.json --execute
```

**Ответ** (200): create возвращает `{"id": "<код>"}` — только код созданного юнита, не полный DTO. Код брать из `id` (не `code`).

**Обязательный `workflow_status`.** Для любого suit с workflow поле обязательно при создании — иначе `HTTP 570 «Не заполнены обязательные поля: 'workflow_status'»`. Передавать начальный транзишн `"workflow_status": {"command": "NEW"}`.

`NEW` — псевдокоманда, а НЕ код действия workflow. Она универсальна: одинаково работает для space с разными workflow. Проверено вживую на `VIEW/task` (`default_workflow`):

| `attributes` | Ответ |
|---|---|
| `{}` | `HTTP 570` «Не заполнены обязательные поля: 'workflow_status'» |
| `{"workflow_status": {"command": "NEW"}}` | `200 {"id": "VIEW-…"}` |
| `{"workflow_status": {"command": "start"}}` — реальный код стартового действия из `GET /rest/api/workflow/v1/suit/{suit}/space/{space}/workflow` | `HTTP 500` |
| `{"workflow_status": {"command": "<несуществующее>"}}` | `HTTP 500` |

Не подставлять сюда коды действий из workflow — они принимаются только в `PATCH /rest/api/workflow/v2/unit/status/change` (`actionCode`) для смены статуса уже созданного юнита, см. раздел «Смена статуса юнита» ниже. При `HTTP 500` на создании первым делом проверять, что в `command` стоит именно `NEW`.

**Правило декомпозиции.** Иерархия идёт сверху вниз: эпик разбивается на задачи, задача — на
подзадачи, и не наоборот. Это ограничение конфигурации типов, а не соглашение: обратную связь
пространство может просто не разрешить (см. «Модель связей»).

**Когда создавать нельзя — отдать ссылку с предзаполнением.** Если пользователь не подтвердил
создание, или не хватает прав, или обязательные атрибуты пространства неизвестны, вместо `create`
можно вернуть готовую ссылку на форму создания:

```text
<база портала>/swtr/units/all/createUnit/init
  ?spaceByCreatingUnit=<код пространства>
  &suitByCreatingUnit=<код типа задачи>
  &summaryByCreatingUnit=<заголовок>
  &descriptionByCreatingUnit=<описание>
  &label=<метка1>,<метка2>
  &<код атрибута>=<значение>
```

Первые три параметра обязательны. Пробел кодируется как `%20`, перенос строки — `%0A`; метки
перечисляются через запятую в одном параметре; любой пользовательский атрибут передаётся парой
«код атрибута = значение». Пользователь открывает форму с уже заполненными полями и жмёт «Создать»
сам — запись выполняет он, а не навык.

**Таблица выше описывает API, а не поведение скрипта.** `swtr_task_tool.py create` подставляет `workflow_status={"command":"NEW"}` сам, если атрибут не передан явно, так что до `HTTP 570` доходят только два случая: подстановка выключена флагом `--no-default-workflow-status` либо не заполнено какое-то другое обязательное поле space. Оба случая скрипт объясняет полем `hint` в ошибке — имя незаполненного поля берётся из тела ответа трекера. Ветка `--body-file` от подстановки свободна: полный контроль тела означает и полную ответственность за обязательные поля.

## Смена статуса юнита (status)

**Модель процесса — `references/workflow-and-approvals.md`**: категории статусов, инварианты схемы
(включая переходы «из любого статуса», которые маршрутизатор обязан учитывать), discovery схемы до
создания юнита и согласования, умеющие менять статус связанных задач. Здесь — механика вызова.

**Статус — не поле, а проекция конечного автомата.** Записать значение в `workflow_status` нельзя: статус меняется выполнением ДЕЙСТВИЯ (перехода), доступного из текущего статуса. Отсюда главные грабли: попытка «присвоить» статус уходит в обновление юнита и получает `HTTP 500 «Что-то пошло не так... Мы уже разбираемся»` — без имени поля и без причины.

Три endpoint-а, и порядок обязателен:

| Шаг | Запрос | Зачем |
|---|---|---|
| 1 | `GET /rest/api/workflow/v1/unit/{code}/status/get?conditionEnabled=true` | `currentStatus`, `availableActions[]`, `actionsExcludedByCondition[]`, `wfSchemaDto` |
| 2 | `GET /rest/api/workflow/v1/workflow/{schemaCode}` | полный граф: `wfTransitions[] = {wfAction, oldStatus, destStatus}` |
| 3 | `PATCH /rest/api/workflow/v2/unit/status/change` | тело `{"unitCode": "…", "actionCode": "…"}` |

Вариант шага 3 с кодами в пути — `PATCH /rest/api/workflow/v1/unit/{code}/status/change/{actionCode}` (без тела).

**Коды действий генерируются для каждой схемы workflow.** «Завершить» в space STS — это `ZVRSHT_lMacNZCcxwjcw`; в другом space у того же по смыслу действия будет другой код. Резолвить в рантайме из `availableActions`, никогда не хардкодить. Единственный стабильный код — `initAction`: псевдопереход создания (он же `{"command":"NEW"}` в create), на существующем юните неприменим.

**Целевой статус часто недостижим за один переход.** Живой пример — `BUG APPSEC v.2.1` (space `STS`, suit `BUG_APPSEC`), 25 переходов: в `RESOLVED` ведёт только действие «Завершить» и только из `PROBLEM ANALYSIS` или `IN PROGRESS`. Из `CANCELLED` доступно ровно одно действие — «Открыто» → `OPEN`. Поэтому `CANCELLED → RESOLVED` — это три перехода, а не один.

**Коды отказов различаются, и это единственный способ понять, что не так** (проверено вживую 11.08.2026 на `STS-452231`):

| Что послали | Ответ |
|---|---|
| `actionCode` из `availableActions` | `200` + `StatusResponseDto` нового состояния |
| валидный код действия, но недоступный из текущего статуса | `HTTP 570` «Случилась непредвиденная ошибка при выполнении валидатора» |
| имя статуса (`RESOLVED`) вместо кода действия | `HTTP 570`, тот же текст |
| `workflow_status` значением в обновление юнита | `HTTP 500` «Что-то пошло не так... Мы уже разбираемся» |

`570` — отказ самой ручки перехода; `500` — признак того, что запрос ушёл не туда. Неудачная попытка статус не меняет.

`actionsExcludedByCondition` — отдельный случай: действие в схеме есть, но закрыто условием (нет прав либо не заполнены поля, которые требует переход). Это не «действия нет», и лечится иначе — поля заполняются ДО смены статуса.

**Команда навыка.** `swtr_task_tool.py status get <код>` — состояние и доступные действия. `status set <код> --to <СТАТУС>` — строит кратчайший маршрут по графу и печатает его; без `--execute` ничего не отправляет. С `--execute` идёт по маршруту, перечитывая состояние перед каждым шагом: если действие стало недоступно, скрипт останавливается с внятной ошибкой и списком доступного вместо `570` от трекера. Переход не идемпотентен, поэтому повторов на запись нет. Цель принимается именем (`RESOLVED`, без учёта регистра) или кодом статуса; `--action <код|имя>` — аварийный люк на ровно один переход.

## Связи между юнитами (link)

Endpoint создания/изменения: `POST /rest/api/unit/v1/link`, тело `{source, destination, type}` (`type` — код типа связи). Поиск: `POST /rest/api/unit/v1/link/find` (`{unitId, types?, direction?, page:{page:{size,page}}}`). Каталог типов: `POST /rest/api/unit/v2/link/types`.

**Правило про русские типы относится к СОЗДАНИЮ связи.** При чтении в живых
данных встречаются любые типы каталога: у одного `CRPV-35498` это `dependend`,
`integration` и `partof`. Читать `link find` так, будто кроме `realized_in` и
`decomposition` типов не бывает, — значит отфильтровать выдачу в ноль. Полный
список типов даёт `link types`.

**Русские типы связей (создаём только их, англ. дубликаты запрещены):**

| Смысл | Код | Направление создания |
|---|---|---|
| состоит из | `decomposition` | `{source: целое/родитель, destination: часть/ребёнок}` |
| реализована в | `realized_in` | `{source: юнит-требование, destination: юнит-контейнер}` |

Направление проверено на живом SWTR: `decomposition` реального эпика — `{source: эпик, destination: story/task}`; `realized_in` — `{source: CRPV-эпик, destination: эпик команды}`.

### Модель связей

Три вида связи, и вид определяет поведение:

| Вид | Направленность | Ограничение |
|---|---|---|
| горизонтальная | симметричная, оба конца равноправны | нет |
| горизонтальная направленная | направленная, у концов разные имена | нет |
| иерархическая | направленная, родитель → ребёнок | **не более одного родителя** |

Ограничение «один родитель» действует **в пределах одного типа связи**. Если в пространстве
настроено несколько иерархических типов, у задачи может быть несколько родителей — по одному на
тип. Не делать вывод «родитель единственный» из самого факта иерархии.

Системные типы, которые есть всегда и не удаляются: **«Декомпозиция»** (отображается как «Состоит
из» / «Является частью» в зависимости от конца) и **«Простая связь»** («Связан с»).

У типа связи **два набора имён**: внутреннее название (видит только конфигуратор) и отображаемое
пользователю название с описанием — **отдельно для каждого узла**. Поэтому одна и та же связь
называется по-разному с двух концов, и поле `relation` в выводе `link find` — это формулировка от
лица запрошенного юнита, а не свойство связи.

Допустимость связи проверяется тройкой «тип пространства + тип задачи A + тип задачи B»: в типе
пространства для каждого типа задачи задан список разрешённых типов связей и допустимых
контрагентов. Отказ в создании связи может означать не отсутствие прав, а запрет этой пары в
конфигурации пространства.

При клонировании задачи связи переносятся, **кроме иерархических**.

### Словарь типов связей для TQL

Функции `linkedUnitsOf()` и `linkedUnitsOfRecursive()` принимают **имя конца связи**
(`sourceName` / `destinationName`), а не название типа и не код — подробности ниже и в
`references/tql.md`. Таблица — словарь названий тенанта в формате «тип → имя от исходного узла /
имя от целевого узла»; именно эти строки и подставляются в функцию.

| Тип | От источника | От цели |
|---|---|---|
| Approval | approves | is approved by |
| Blocks | blocks | is blocked by |
| Bugs | is a bug for | contains bugs |
| Checklist | checks | is checked by |
| Child Issue | is parent task of | is child task of |
| Cloners | clones | is cloned by |
| Dependend | depends on | is depended on by |
| Duplicate | duplicates | is duplicated by |

## Атрибуты юнита

**Пустой `attributes` без сужения по типам задач.** `POST /rest/api/unit/v3/find` возвращает
`attributes` пустыми, если в фильтре не сужены `suits`: ошибки нет, юниты приходят, а атрибуты —
нет. Проверено вживую. При «пропавших» атрибутах первым делом добавлять `--suit`.

**Справочники компонентов и версий — по пространству**, ключ тела запроса — `space` (не `spaceCode`
и не объект). Тоже проверено вживую.

Модель атрибутов (источник — документация АС21):

- **Зарезервированные коды**, которые нельзя занять пользовательским атрибутом: `summary`, `code`,
  `type`, `space`, `description`. Это и есть системные поля юнита.
- Тип **«Таксономия»** — перечисление, у каждого значения свои **код и отображаемое значение**; в
  фильтрах и в TQL (`priority`, поисковое поле `taxonomy.code`) сравнивается код.
- Удаление используемого значения таксономии — это **блокировка**, а не удаление: значение остаётся
  в старых задачах, но недоступно для новых, и может быть восстановлено. Поэтому в выдаче
  встречаются значения, которых нет в списке доступных.
- **Скоуп атрибута**: глобальный справочник тенанта → включается в тип задачи (со значением по
  умолчанию) → тип задачи входит в тип пространства → пространство. Удаление атрибута из типа
  задачи **не стирает значения**: они скрываются и возвращаются, если атрибут вернуть.
- Справочники уровня пространства: **Компоненты** и **Версии**.

## Версии, компоненты и код продукта

Проверено записью 14.08.2026 (создана `PVM-175448`, значения прочитаны обратно).

**Код атрибута зависит от типа задачи** — это первое, обо что спотыкается ручная попытка:

| Поле | `task` | `story` | `epic_crpv` |
|---|---|---|---|
| Fix Version | `fix_version` | `fix_version` | `fix_version_s` |
| Affects Version | `affects_version` | `affects_version` | `affects_version_s` |
| Компонент | `sber_component` (рядом есть `component_s`) | `component_s_crpv` | `component_s` |
| Код продукта | `customfield_24900` | `customfield_24900` | нет |

**Форма значения зависит от типа поля, а не от того, мультизначное оно:**

| Тип поля | Форма | Пример |
|---|---|---|
| `taxonomy` (код продукта) | голый код **строкой** | `"273841"` |
| `version`, `sber_component` | список **объектов** | `[{"code": "81a0a9f4-…"}]` |

Список голых строк для ссылочных полей трекер отвергает `HTTP 500`. Код продукта числом вместо
строки — тоже неверная форма.

**Справочники привязаны к пространству**, одно имя в разных пространствах имеет разные коды:

- компоненты — `POST /extension/plugin/v2/rest/api/sber_components_plugin/v1/component/find`
- версии — `POST /extension/plugin/v2/rest/api/swtr_task_tracker_plugin/v1/version/find`
- коды продукта — прямо в схеме типа, в `directoryValues` атрибута `customfield_24900`

Всё это закрыто командами: `attributes <suit>` показывает поля типа и коды под человеческие имена,
`directory --space … --kind components|versions|product` — значения справочника, а у `create` есть
флаги `--fix-version`, `--affects-version`, `--component`, `--product`, принимающие **имена**
(сценарий §21b).

**Изменение существующей задачи** — `PATCH /rest/api/unit/v2/update/{code}`, ответ
`{"id": "<код>"}`. Форма пути неочевидна: **глагол стоит перед кодом**, поэтому
`/rest/api/unit/v2/{code}/update` отвечает `404` (на поиск ушло около 40 проб). Команда навыка —
`update` (сценарий §21c): дифф «было → станет» до записи, отказ на попытку сменить статус, запись
без повторов и обратное чтение после.

### Что и в какой форме принимает патч

Проверено записью 14.08.2026 на `PVM-175448` (suit `task`, space `PVM`):

| Что меняем | Тип поля | Форма значения |
|---|---|---|
| Приоритет, код продукта | `taxonomy` | голый код **строкой**: `"blocker"`, `"273841"` |
| Fix/Affects Version | `version` | список объектов: `[{"code": "<uuid>"}]` |
| Компонент | `sber_component` | список объектов: `[{"code": "<uuid>"}]` |
| Трудозатраты, сложность | `non_negative_int` | **число**: `3` |
| Контрольный срок | `date_time` | строка ISO: `"2026-09-01T00:00:00Z"` |
| Метки | `label` | список **строк**: `["guru-test"]` |
| Исполнитель | `user` | **голая строка** `externalId`: `"Familia.I.O"` |
| Папка тест-кейса | `folder` | **голая строка** кода: `"550c265e-…"` |
| Предусловие, тело wiki | `wisiwig`, `wiki_page_wisiwig` | **строка** с документом ProseMirror внутри |
| Шаги тест-кейса | `test_step` | **объект-обёртка** `{"testStepList": [ … ]}` |
| Название, описание | базовые поля | **на верхнем уровне тела**, не внутри `attributes` |

У поля типа `user` объект и список дают `HTTP 500` — принимается только строка. Название и описание
внутри `attributes` трекер просто не увидит.

**Четыре поля читаются НЕ в той форме, в какой пишутся** — `user`, `folder`, `wisiwig` и
`test_step`. Отдать обратно прочитанное у первых трёх значит получить `HTTP 500` без имени поля, а
у `test_step` — `200` и молча пустые шаги. Команды `create` и `update` приводят форму сами; формы и
проверочные юниты — в `references/test-management-system.md` и `references/wiki-model.md`.

### Две ловушки патча

**Невалидный код таксономии проходит с `200` и молча не сохраняется.** Патч `priority: "high"`
(в этом пространстве коды `blocker/critical/major/minor/trivial`) ответил `200`, а поле осталось
пустым. Отсюда обязательное обратное чтение: успешный код ответа не доказывает, что значение легло.

**Патч валидирует обязательные поля всего юнита, а не только изменяемые.** Если у задачи не
заполнен обязательный атрибут, **любой** патч падает с `570 Не заполнены обязательные поля: '…'` —
даже тот, который этого поля не касается. Лечится заполнением названного поля, можно тем же патчем.

Проверять, какие поля обязательны и какие у них допустимые значения, — командой `attributes <suit>`.

## Массовые операции и импорт

Ограничения, которые определяют, что вообще можно обещать пользователю (источник — документация
АС21; команд навыка для этих операций нет, они выполняются в UI):

- **Массовые операции** требуют минимум двух задач. Массовая смена статуса возможна только в
  статус, доступный **всем** выбранным задачам; массовое редактирование — только по атрибутам,
  общим для всех выбранных. Поддерживается очистка значения.
- **Массовый перенос** между пространствами требует прав во всех задействованных пространствах и
  включает два сопоставления: типов задач и статусов. Смена типа без переноса — это перенос в то же
  пространство.
- **CSV-импорт** требует двух файлов: CSV с данными и JSON-конфига. Обязательные колонки —
  `UnitType` и `Summary`; без любой из них строка не импортируется. Кодировки — UTF-8 или
  Windows-1251, разделитель обязан совпадать с указанным в конфиге; режимы преобразования колонок —
  `asIs` и `skip`.
- **Не импортируются** вовсе: `created_at`, `updated_at`, `created_by`, `updated_by`, массивы,
  множественная таксономия и атрибуты плагинов.

Импорт CSV — реальная альтернатива серии `create`, когда заводится десяток задач декомпозиции. Но
это ручная операция пользователя: навык готовит файл, а не выполняет импорт.

## Вложения юнита

```bash
python3 $SKILL_DIR/scripts/swtr_task_tool.py attachments CRPV-106611
```

`GET /rest/api/unit/files/v2/<КОД>?safe=true` — перечень файлов юнита. Проверено на
portal 18.08.2026: HTTP 200, тело `{"content": [...], "totalElements": N}`, у записи
есть `fileId`, `filePathParsedDto.fileName`, `fileMetadataDto.{contentType,contentLength}`,
`createdBy` и `fileNotFound`. Юнит без вложений отдаёт пустой `content`, а не ошибку.

`safe=true` обязателен: без него метод падает, когда файла нет в S3, и вместо перечня
вызывающий получает отказ по всему юниту. Пропавший файл виден в выводе полем

## Правила write-action

Реальный POST выполнять только если пользователь явно попросил создать задачу. Если есть неопределенность по space, suit, summary, description, обязательным атрибутам или согласованию, сначала сделать dry-run и задать вопрос.

**Значение, взятое из профиля, назвать пользователю до `--execute`.** Пространство, тип, продукт и компоненты могут прийти не из запроса, а из умолчаний (`defaults_applied`, `source: profile`), и человек об этом узнаёт только из ответа. Запись в чужое пространство или с чужим продуктом дороже одной лишней фразы в предпросмотре.

**Запись подписывает на уведомления.** Получатели уведомлений по задаче — автор, исполнитель и
наблюдатели, а в наблюдатели **автоматически** попадает каждый, кто задачу редактировал или
комментировал. То есть комментарий от лица пользователя молча подписывает его на всю дальнейшую
переписку по задаче. Автор самого изменения уведомление о нём не получает.

## Назначенные задачи (assigned)

Сценарий показывает задачи, назначенные на одного или нескольких пользователей.

**Пользователь задаётся логином, а фильтр сравнивает `externalId`.** Атрибут
`assigned_to` имеет тип `user`: `assigned_to in ("savinov.m.y")` находит ноль
задач там, где `("Savinov.M.Y")` находит все — регистр значим. Скрипт сам
сопоставляет логин с `externalId` через `POST /rest/api/user/v1/find` (тело —
голый массив логинов в нижнем регистре) и кладёт результат в поле
`assigneeValues` вывода, а в `notes` пишет, как именно логин был сопоставлен.
Логин, которого нет в справочнике, не выбрасывается: в фильтр идут и он сам, и
его title-case вариант (`sa-robot` → `sa-robot`, `Sa-robot`), с отдельной
заметкой. Если резолв недоступен, команда всё равно выполняется на тех же
кандидатах — диагностировать пустую выдачу без запроса невозможно.

**`--me` резолвится по цепочке** `SWTR_LOGIN` → профиль (`login`) → `USER` → логин Basic-креда `SWTR_BASIC_AUTH`. Источник приходит в `defaults_applied` (`env`, `profile`, `os_user`, `credential`) и отдельной строкой в `notes`. Ни один источник не дал логина — команда отказывается и перечисляет способы его задать. Отключение профиля — `--no-profile`, явный логин — `--user LOGIN`.

`--space` не задан — область берётся из профиля (`task_tracker.primary_space`, затем `task_tracker.spaces`); что взято, видно в `defaults_applied` и строкой в `notes`. Отключить — `--no-profile`.

Базовый запрос (один пользователь, без фильтра по статусу):

```bash
python3 $SKILL_DIR/scripts/swtr_task_tool.py assigned --user vasiakuzyakin --space PVM --status all --limit 50
```

Фильтрация по статусу:

- `--status all` — без условия по статусу, только `assigned_to in (...)`.
- `--status in-progress` — добавляет `workflow_status not in ("done","closed","resolved","rejected")`.
- `--status <value>` — добавляет `workflow_status = "<value>"`. Подходит для конкретных значений workflow в нужном space.

Endpoint — **всегда TQL**:

```http
POST /rest/api/unit/v3/find/tql
```

Атрибутный фильтр обычного `/rest/api/unit/v3/find` по `assigned_to` не матчит
ничего ни в одном формате значения (логин, `externalId`, объект пользователя,
ФИО), хотя тот же запрос без фильтра юниты отдаёт. Именно из-за него сценарий
раньше молча возвращал пустой список: ошибки нет, данных нет.

TQL для `--status all` и `--status in-progress`:

```text
assigned_to in ("Vasiakuzyakin.I.I") and space in ("PVM")
assigned_to in ("Vasiakuzyakin.I.I") and workflow_status not in ("done", "closed", "resolved", "rejected") and space in ("PVM")
```

UNCONFIRMED:

- Атрибут `workflow_status` существует в большинстве space-ов, но конкретный набор значений зависит от workflow. При пустой выдаче запустить `assigned --status all` и посмотреть значения статуса в выдаче.
- Если space хранит статус под другим кодом атрибута, передать его явно через `--status <value>` как уточняющий фильтр или ограничиться `--status all`.

## Выполненные задачи за неделю (done-weekly)

Сценарий показывает задачи, переведенные одним пользователем или группой в «done»-статусы за окно по умолчанию 7 дней.

Базовый запрос:

```bash
python3 $SKILL_DIR/scripts/swtr_task_tool.py done-weekly --user vasiakuzyakin --space PVM --days 7
```

Группа сотрудников и явная дата:

```bash
python3 $SKILL_DIR/scripts/swtr_task_tool.py done-weekly --user vasiakuzyakin --user maxisavinov --space PVM --since 2026-04-30
```

Endpoint:

```http
POST /rest/api/unit/v3/find/tql
```

Используется TQL, потому что нужны одновременно фильтры по `assigned_to`, `workflow_status` и `updatedAt >= <date>` (последнее не поддерживается обычными property filters в общем виде).

Тело:

```json
{
  "query": "assigned_to in (\"Vasiakuzyakin.I.I\", \"Maxisavinov.M.Y\") and workflow_status in (\"done\", \"closed\", \"resolved\", \"rejected\") and updatedAt >= \"2026-04-30T00:00:00Z\" and space in (\"PVM\")",
```

Опции:

- `--days N` — окно в днях. Игнорируется, если задан `--since`.
- `--since YYYY-MM-DD` — явная нижняя граница (включительно). Скрипт достраивает её до
  `YYYY-MM-DDT00:00:00Z`: голую дату TQL отвергает как некорректное значение для типа
  `date_time`, из-за чего отчёт падал с HTTP 400. Значение со временем передаётся как есть.
- `--done-status STATUS` — повторяемый набор «done» статусов. По умолчанию `done, closed, resolved, rejected`.
- `--space SPC` — повторяемый. Не задан — пространства профиля, источник в `defaults_applied` и `notes`; отключение — `--no-profile`.
- `--me` — логин по той же цепочке, что в `assigned`: `SWTR_LOGIN` → профиль → `USER` → логин Basic-креда.

UNCONFIRMED и важные ограничения:

- В качестве признака «выполнено» используется `updatedAt >= <since>` плюс `workflow_status in <done-set>`. В выборку попадают также задачи, которые были закрыты раньше, но переоткрыты или просто отредактированы внутри окна. Если space ведет реальный `closedAt` или историю переходов, эти источники здесь не используются — нужно фиксировать ограничение в ответе.
- Список «done» статусов (`done, closed, resolved, rejected`) подобран по дефолту; для конкретного space передать `--done-status` явно.
- При пустой выдаче проверить, существует ли `workflow_status` в этом space, и какие именно значения статуса используются.
- Пользователь резолвится так же, как в `assigned`: логин → `externalId` через `POST /rest/api/user/v1/find`, результат виден в поле `assigneeValues` и в `notes`.

## Когда переходить с обычных find-фильтров на TQL

**Синтаксис языка — `references/tql.md`.** Здесь только правило выбора; операторы по каждому
атрибуту, функции и ограничения движка не дублируются.

- Обычный `find` достаточен, когда нужны фильтры по `space`, `suit`, конкретному значению атрибута, по `properties.like/eq/in/ge/le`.
- По `assigned_to` (и любому другому атрибуту типа `user`) обычный `find` НЕ фильтрует — он отдаёт пустую выдачу без ошибки. Такие условия только через TQL.
- TQL (`find/tql`) нужен, когда требуется `not in`, фильтр по date-range (`updatedAt >= ...`), категория статуса (`statusCategory()`) или обход связей (`linkedUnitsOf[Recursive]()`).
- Комбинации `or`/`and` TQL поддерживает **ограниченно**: только чистый AND либо чистый OR, без скобок. Смешанная форма не отвергается, а тихо фильтрует неверно — сверяться с `references/tql.md` перед выполнением.
- В TQL значения цитируются как `"value"`, даты — как `"YYYY-MM-DDTHH:MM:SSZ"` (голая дата отвергается для типа `date_time`). Для повторяемости запроса использованный TQL возвращается в поле `tql` JSON-вывода; при необходимости агент приводит его в ответе пользователю под заголовком «TQL».
