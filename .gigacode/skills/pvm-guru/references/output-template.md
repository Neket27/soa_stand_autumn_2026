# Шаблон итогового отчета

Итоговый отчет всегда писать на русском языке. Не оставлять пустые разделы и служебные заглушки. Если данных нет, писать, какие источники проверены и что именно не удалось подтвердить.

## Файл результата

Сохранять отчет в `docs/ai/<slug>/<YYYY-MM-DD>-review.md`. Для SWTR-юнита slug начинается с кода в нижнем регистре. Для локального файла slug строится из имени файла. Для ответа по SourceControl использовать `docs/ai/source-control/<project>/<repo>/<topic>/`.

## Структура ответа по коду

Использовать, когда пользователь спрашивает, как реализована функция или есть ли она в репозитории.

```markdown
# Проверка реализации в коде

## Что искали

## Где искали

## Что найдено

## Интерпретация найденного

## Что не найдено

## Ограничения проверки

## Следующие действия
```

В разделе «Где искали» обязательно указать SourceControl tenant, project, repo, ref и path-prefix либо локальные пути. Если repo не был указан и показаны только кандидаты, не делать выводов по коду.

## Структура ответа «wiki + код»

```markdown
# Сопоставление документации и кода

## Что написано в задаче/wiki

## Термины, которые проверялись в коде

## Что найдено в коде

## Где есть совпадение документа и реализации

## Где есть расхождение или пробел

## Ограничения проверки

## Рекомендации
```

## Паспорт проверки

Указать:

- дата проверки;
- входной источник;
- код SWTR-юнита или имя локального файла;
- тип документа: CR, PRD, системные требования, архитектурная постановка или смешанный документ;
- проверялись ли SWTR/Wiki, локальные документация и код, SourceControl;
- ограничения проверки.

## Краткий вывод

Дать 3–7 предложений:

- что предлагается изменить;
- насколько постановка готова к оценке и реализации;
- главные блокеры;
- главные риски;
- следующее действие.

## Трассировка требований

Для требований использовать таблицу:

```markdown
| ID | Тип | Важность | Формулировка | Способ проверки | Статус трассировки |
|---|---|---|---|---|---|
```

Статус трассировки:

- `полная`: есть требование, декомпозиция и проверка;
- `частичная`: один из элементов слабый или неполный;
- `нет проверки`: нет способа подтвердить выполнение;
- `нет декомпозиции`: требование слишком крупное для оценки;
- `конфликт`: требование противоречит другому разделу или источнику.

## Актуальность относительно документации и кода

Разделять источники:

- SWTR/Wiki;
- локальная документация;
- локальный код;
- SourceControl project/repo/ref.

Формулировки:

- «подтверждено в коде» — есть конкретные файлы и строки;
- «частично подтверждено» — найдены термины или похожие места, но не полный сценарий;
- «не найдено в проверенной области» — поиск выполнен, совпадений нет;
- «не проверялось» — не было источников, доступа или параметров.

## Замечания

Каждое замечание оформлять так:

```markdown
### C-1: Короткое название проблемы

**Категория:** `C` / `L` / `D`  
**Источник:** SWTR unit CRPV-35498, поле Description; SourceControl pvm/pvm-backend:src/main/App.java:42  
**Контекст:** Короткая цитата или пересказ конкретного места.  
**Проблема:** Почему это мешает оценке, реализации, эксплуатации или приемке.  
**Рекомендация:** Что именно добавить, изменить или согласовать.  
**Кому адресовать:** заказчик / SO / архитектор / команда разработки / эксплуатация / КБ.
```

Нумерация идет отдельно по категориям: `C-1`, `C-2`, `L-1`, `D-1`.

## Вопросы

Вопросы формулировать как рабочий список для уточнения. Каждый вопрос должен быть связан с замечанием или риском и содержать адресата.

```markdown
| Адресат | Вопрос | Зачем нужен ответ | Связанное замечание |
|---|---|---|---|
```

## Итоговая оценка готовности

Выбрать один статус:

- `готово к разработке`: критичных и логических блокеров нет, оставшиеся замечания не мешают реализации.
- `нужны точечные уточнения`: есть небольшие пробелы, оценку можно дать с ограничениями.
- `нужна существенная переработка`: много пробелов по требованиям, NFR, интеграциям или приемке.
- `блокер для оценки`: без устранения C-замечаний невозможно оценить или безопасно реализовать.

Обязательно дать краткое обоснование статуса.

## Статистика проверки

Указать:

- количество использованных источников;
- количество локальных путей, если проверялись;
- количество SourceControl-репозиториев и веток, если проверялись;
- количество найденных замечаний `C`, `L`, `D`;
- количество открытых вопросов;
- были ли найдены TODO, TBD, красные флаги или нерешенные вопросы в исходном документе;
- что не проверялось и почему.
