# SWTR PRD, Task Tracker and SourceControl Review

## Каталог навыка (`$SKILL_DIR`)

Все примеры запуска в этом файле и в остальных файлах навыка начинаются с
`$SKILL_DIR` — это каталог самого навыка, а НЕ каталог проекта пользователя.
У установленного пользователя навык лежит в домашнем каталоге, а агент запущен
в его проекте, поэтому путь вида `.gigacode/skills/pvm-guru/…` там не существует.

Определи `$SKILL_DIR` один раз в начале работы и подставляй во все команды:

```bash
for d in ".gigacode/skills/pvm-guru" \
         "$HOME/.agents/skills/pvm-guru" "$HOME/.gigacode/skills/pvm-guru" \
         "$HOME/.claude/skills/pvm-guru" "$HOME/.config/opencode/skills/pvm-guru" \
         "$HOME/.codex/skills/pvm-guru"; do
  [ -d "$d" ] && SKILL_DIR=$(cd "$d" && pwd) && break
done; echo "$SKILL_DIR"
```

Путь должен быть абсолютным (отсюда `cd … && pwd`): субагенты и отдельные вызовы
шелла стартуют в своём cwd, и относительный путь у них сломается. Если ничего не
нашлось — скажи об этом прямо и не выдумывай путь.

## Назначение

Универсальный рабочий инструмент для SWTR Task Tracker, SWTR Wiki, локальной документации, локального кода, SourceControl, а также Confluence и Jira на хосте `sberworks` (крайний приоритет, см. «Приоритет систем»). Классы задач:

1. Ревью CR, PRD, системных требований и архитектурных постановок перед оценкой или передачей в разработку (ревью ДОКУМЕНТОВ; ревью PR/кода — навык `guru-pr-review`).
2. Быстрый поиск знаний: что за задача, какие задачи и wiki похожи, где описано, в каком репозитории и как реализовано.
3. Создание задач и комментарии в SWTR Task Tracker, создание и правка страниц вики с текстом
   (write только через `--execute`).
4. TMS: тест-планы, циклы, прогоны, папки — read-only; тест-кейс создаётся и правится общими командами `create --suit test_case` / `update`.
5. Аналитика Task Tracker: задачи, назначенные на сотрудника, и выполненные за неделю.
6. Confluence и Jira на `sberworks` (только по явному признаку, см. «Приоритет систем»): открыть/найти страницу или задачу, поиск по тексту/CQL/JQL, похожие, комментарии; write только через `--execute`.
7. Диагностика доступа к любой из 4 систем без утечки секрета.

## Приоритет систем (обязательное правило)

Порядок по умолчанию:

1. **SWTR Task Tracker + SWTR Wiki** (`portal`) — задачи, юниты, вики.
2. **SourceControl** (`portal`) — код, репозитории, PR.
3. **Локальные файлы** — только по явно заданным путям (`@local-docs`/`@local-code`).
4. **Jira / Confluence** (`sberworks`) — ТОЛЬКО по явному признаку.

**Явный признак sberworks** (достаточно одного):

- слово «Jira», «жира», «Confluence», «конфлюенс», «sberworks» в запросе пользователя;
- ссылка на `sberworks.ru`;
- пользователь уже подтвердил переход в sberworks для этого же кода или запроса.

**Голый код `PVM-…` / `CRPV-…` явным признаком НЕ является.** Проекты `PVM` и
`CRPV` реально существуют в обеих системах: `PVM-53979` — юнит SWTR, `PVM-52489` —
задача Jira. Код сам по себе систему не определяет, поэтому по умолчанию — Task Tracker.

**Если в Task Tracker не нашлось:** сказать «в Task Tracker не найдено», задать
ОДИН вопрос «посмотреть в Jira sberworks?» и ЖДАТЬ ответа. Без ответа не ходить.

`jira_tool.py` и `confluence_tool.py` требуют флаг `--confirm-sberworks`; без него
они отказываются работать с `gate: "sberworks-not-default"` и не делают ни одного
сетевого вызова. Ставить флаг только при выполненном явном признаке.
`guru_doctor.py` флага не требует и проверяет все 4 системы всегда.

Для sberworks-задач и страниц `pvm-guru` — основной навык: чтение, поиск, похожие,
комментарии, создание и правка задачи Jira, правка существующей страницы Confluence.
Операций записи, которых у него нет — создание страницы Confluence, вложение,
комментарий к странице, worklog Jira, связь задач и привязка к эпику, смена статуса, —
касается отдельный навык `mcp-atlassian`. Он не перехватывает вопросы про задачи:
любой запрос вида «что за задача»/«дай инфу по задаче» и любой голый код — это
`pvm-guru`.

## Контракт вывода скриптов

Все скрипты навыка печатают результат в stdout как один JSON-объект (кроме `guru_doctor.py` — он печатает человекочитаемую диагностику). В каталог проекта не пишет ни один из них; файлы на диске появляются ровно в трёх названных местах:

- **отчёт о ревью** (`docs/ai/<slug>/<YYYY-MM-DD>-review.md`) — его пишет **агент** своими файловыми инструментами после анализа stdout, а не скрипт;
- **профиль умолчаний** (`~/.config/pvm-guru/profile.json`) — его пишет `guru_profile.py` (`set`, `unset`, `reset`), единственный писатель профиля; агент этот файл руками не правит (раздел «Профиль пользователя и умолчания»);
- **env-файл с кредами** (`~/.swtr-review.env`) — его пишет `guru_env_setup.py`, единственный писатель секретов (раздел «Безопасность секретов»).

Применённое умолчание скрипт печатает в поле `defaults_applied` — оно тоже часть контракта вывода, разбор в разделе «Профиль пользователя и умолчания».

Финальные ответы пользователю — на русском.

Поддерживаемые входы: локальный файл (`.md/.xml/.html/.docx/.txt/.json/.pdf`); SWTR-ссылка (`.../swtr/wiki/unit/PVM-53979?...`); код юнита (`PVM-53979`, `CRPV-35498`); строка с ключевыми словами; SourceControl проект/репозиторий/ref; Confluence-страница sberworks (URL или `pageId`); Jira-ключ sberworks; локальные пути.

### Веб-ссылка на юнит трекера

**Ссылку не собирай — бери готовую из вывода скрипта.** Её кладут туда сами скрипты:

- поле `url` — там, где юнит один: `get` по коду, `create` после записи, источник
  `fetch_swtr_sources.py`, каждая строка `created` в отчёте декомпозера;
- карта `urls` (`код → ссылка`) — там, где в выводе лежит сырой ответ трекера:
  `search`, `similar`, `tql`, `assigned`, `done-weekly`, `swtr_unit_search.py` и любой
  другой вывод, где встретился код юнита.

Единственная разрешённая форма — `{SWTR_BASE_URL}/units/all/unit/<КОД>`, по умолчанию:

```
https://portal.works.prod.sbt/swtr/units/all/unit/PVM-175194
```

Собирать её руками нужно только там, где скрипт не звали вовсе. Форму **нельзя
восстанавливать по аналогии с другими трекерами**. API её не отдаёт: у ответа
`GET /rest/api/unit/v2/{code}` нет ни одного поля со ссылкой, поэтому единственный
источник формы — это правило. Формы ниже в SWTR **не существуют**, любая из них ведёт
пользователя в никуда:

- `…/swtr/task/<КОД>` — форма чужого трекера;
- `…/swtr/browse/<КОД>` — форма Jira;
- `…/swtr/<КОД>` — код сразу за базовым адресом.

Отдельные случаи:

- `…/swtr/units/current/unit/<КОД>?space=…` — рабочая ссылка, но привязана к space. Как **вход** от пользователя принимается, сам не собирай: space известен не всегда.
- `…/swtr/wiki/unit/<КОД>` — вики-страница юнита, а не карточка. Давать только когда пользователь просил именно вики.

Когда кода юнита нет или он не подтверждён чтением — ссылку не выдумывать, а назвать код
и сказать, что ссылку не собрать.

## Профиль пользователя и умолчания

Локальный файл `~/.config/pvm-guru/profile.json` хранит умолчания пользователя: логин в трекере, роль, основное пространство и пространства в поле зрения, тип задачи, продукт и компоненты, tenant, проект и репозитории SourceControl, ключ проекта Jira и пространства Confluence. Собирается разговором в `/guru-start`, правится командой `/guru_profile` (сценарий 25). Скрипты навыка его только читают.

- **Порядок источников — явное → окружение → профиль → прежнее поведение.** Названное пользователем всегда сильнее профиля: если он назвал пространство, тип задачи, проект или репозиторий — передавай их флагами, профиль в дело не идёт. Профиль закрывает только пропуск, а если пусто и там — работает прежнее поведение: тот же текст ошибки argparse и тот же код возврата 2, что до появления профиля. Логин для `--me` разрешается в порядке `SWTR_LOGIN` → профиль → `USER` → логин Basic-креда.
- **Применённое умолчание называй одной фразой.** Источник значения приходит из вывода структурно — список `defaults_applied` с записями `{key, value, source}`, где `source` — `profile`, `env`, `os_user` или `credential` (явно названное в него не попадает вовсе, пустой список не печатается). У выборок (`assigned`, `done-weekly`, `search`, `count`, `similar`) то же сказано готовой строкой в `notes` — её и пересказывай, а не сочиняй свою. В ответе — одна фраза: что взято из профиля и как выполнить без него («искал в пространствах профиля PVM и CRPV; чтобы искать везде — повтори без профиля»). Источник не додумывай: бери из `defaults_applied`, а не из памяти.
- **Разово обойти профиль — флаг `--no-profile`.** Он есть у `swtr_task_tool.py`, `source_control_search.py`, `source_control_pr.py`, `jira_tool.py` и `confluence_tool.py`: файл не читается вовсе, и вызов ведёт себя как у пользователя без профиля. Этим и исполняются просьбы «найди везде», «по всем пространствам», «без моих умолчаний». Выполнив с `--no-profile`, **скажи одной строкой, что умолчания профиля не применялись** — иначе ответ неотличим от ответа человеку без профиля, и он не увидит, что его сохранённую область поиска намеренно проигнорировали. Область выборки, взятая из профиля, названа в `notes` при любом результате; у пустой выдачи та же строка ещё и подсказывает, как расширить область.
- **Репозитории из профиля предлагай первыми.** Репозиторий из профиля сам не подставляется — выбор остаётся за человеком. Когда он не назван, список из профиля приходит отдельным полем `profileRepos` и в выдаче `source_control_search.py repos`, и у `search` без `--repo`: предлагай его первым. Листинг кандидатов отфильтрован поисковым запросом, поэтому знакомого репозитория в нём может не быть вовсе — на `candidates` не опирайся. Те из них, что встретились в самой выдаче, перечислены рядом отдельным полем `profileRepoMatches` — сырой ответ API при этом не дописывается. Ни того, ни другого поля нет, когда список в профиле пуст или чтение отключено `--no-profile`.
- **Профиль — не секрет и секретов не содержит.** В нём только то, что пользователю можно показать; пароли, токены и Basic-строки живут в `~/.swtr-review.env` и настраиваются через `/guru_doctor`. Ключ, чьё имя похоже на секрет (`TOKEN`, `PASSWORD`, `AUTH`, `COOKIE`, `SECRET`), `guru_profile.py` на запись отклоняет и удаляет из файла при ближайшем сохранении; диктует токен — откажись и отправь к `/guru_doctor`.
- **Правка профиля — это названный ключ плюс намерение запомнить.** Просьба идёт в профиль, когда в ней есть и ключ (логин, роль, пространство, тип задачи, продукт, компоненты, tenant/проект/репозиторий SourceControl, проект Jira, пространство Confluence), и слова «профиль», «по умолчанию», «запомни», «сделай основным» или равнозначные. Ключ не назван («запомни это», «сохрани, как сейчас») — **спроси, какое умолчание записать, и до ответа не сохраняй ничего**. Фразу, которую можно прочитать и как правку профиля, и как контекст проекта («настрой контекст», «настрой гуру»), разрешай одним вопросом с двумя вариантами — профиль пользователя или контекст-пак `guru-context`, — а не догадкой; фразы-исключения перечислены в сценарии 25.
- **Профиля может не быть.** Статусы `missing`, `corrupt` и `unsupported` означают одно и то же для работы: веди себя как без профиля, значения спрашивай, как раньше. Состояние файла и причину показывают блок `profile state` в `guru_doctor.py` и команда `/guru_profile`; чинить JSON правками из агента не нужно.

### Выбор между перекрывающимися точками входа

- **`swtr_task_tool.py get` vs `fetch_swtr_sources.py`** — `get` даёт быструю карточку/lookup (`summary + unit + wiki`); `fetch_swtr_sources` собирает ПОЛНЫЙ источник для ревью (`+ description + attributes + извлечённые длинные wikiTexts`, а также локальные файлы). Для ревью документа (сценарий 4) — `fetch_swtr_sources`.
- **`fetch_swtr_sources.py` vs `spec_sources.py`** — `fetch` читает ОДИН юнит (его карточку и его же вики) и годится, когда источник заведомо самодостаточен: ревью одного документа (сценарий 4). `spec_sources` дочитывает ещё и названное связанным — связи трекера и коды юнитов из текста — и нужен там, где по постановке пишут спецификацию (сценарий 26). Обход стоит лишних запросов: если связи не нужны, берите `fetch`.
- **`spec_sources.py` vs `openspec_seed.py`** — `spec_sources` СОБИРАЕТ материал, `openspec_seed` раскладывает его по скелету proposal. Это два шага одного пути, а не выбор: вывод первого принимается вторым через `--source-file`.
- **`swtr_task_tool.py search` vs `swtr_unit_search.py`** — `search` высокоуровневый (OR по `code/summary/description` + wiki, `--common-attributes`); standalone `swtr_unit_search.py --body-file` даёт полный контроль `QLRequestDto` (сложные фильтры, `--filter`, `--count`). Обычный запрос → `search`; сложный QL → `swtr_unit_search`.
- **Комментарии** — всегда отдельный read-only `swtr_unit_comments.py` (сабкоманды в `swtr_task_tool.py` для этого нет).
- **Шаги тест-кейса vs тело вики** — шаги живут в атрибуте `test_step` и пишутся `create`/`update --step`/`--steps-file` (сценарий 13a); тело вики — отдельный атрибут `wiki_page_body` (сценарий 24). Таблица, записанная в тело вики кейса, шагами не станет: редактор шагов читает `test_step`. Пустое тело вики у кейса — не признак того, что шаги хранятся там.
- **SWTR vs sberworks** — по умолчанию ВСЕГДА `swtr_task_tool`/`fetch_swtr_sources`. В `jira_tool`/`confluence_tool` уходить только при явном признаке sberworks — полный список признаков в «Приоритет систем». Голый код задачи и запрос без ссылки — это Task Tracker, а не Jira.

## Смежные навыки (когда НЕ pvm-guru)

`pvm-guru` — доступ к задачам/вики/коду/TMS и **ревью ДОКУМЕНТОВ**. Для соседних задач есть отдельные навыки. Матрица входов/выходов и handoff-рецепты — в `docs/guru-family.md`.

| Запрос пользователя | Навык | Почему не pvm-guru |
|---|---|---|
| Оценить трудозатраты, чел-дни, декомпозиция по фазам | `estimation-service` | pvm-guru оценивает КАЧЕСТВО документа, не трудозатраты |
| Ревью Pull Request / изменений кода | `guru-pr-review` | pvm-guru ревьюит ДОКУМЕНТЫ (PRD/CR/требования), не PR. **Создание** PR — здесь, сценарий 19 (`source_control_pr.py`); ревью созданного — там |
| Декомпозиция постановки в атомарные требования (CSV) | `prd-requirement-decomposer` | pvm-guru собирает/ревьюит документ, не строит `requirements.csv` |
| Декомпозировать эпик CRPV в задачи команды (эпик + истории + связи) | `guru-crpv-decomposer` | pvm-guru даёт примитивы (`create`, `link`, `suits`), но не владеет методологией нарезки эпика и INVEST-гейтом |
| Переписать сырой тикет в задачу для кодинг-агента | `agent-task-rewriter` | pvm-guru читает/ревьюит, не нормализует постановку под агента |
| Спланировать работу / исполнить план | `plan` / `exec` | план и исполнение — отдельный цикл (`docs/plans/*.md`) |
| Продумать идею до дизайна, разобрать варианты | `guru-brainstorm` | pvm-guru даёт контекст, но не ведёт проработку диалогом |
| Проверить утверждение: аргументы за и против | `guru-dialectic` | pvm-guru оценивает документ, а не проверяет отдельный тезис по коду |
| Найти причину ошибки, падения сборки, деградации | `guru-root-cause-investigator` | это разбор поломки, а не документа; 401/403 к системам — `/guru_doctor` |
| Написать комментарий, описание PR, замечание ревью | `guru-writing-style` | pvm-guru порождает содержание, стиль текста наружу — отдельный слой |

Признак `guru-pr-review`: во входе SourceControl-ссылка `…/pulls/<id>` — это всегда ревью PR, даже если сказано просто «ревью». Handoff `pvm-guru → estimation-service / prd-requirement-decomposer / agent-task-rewriter`: агент сохраняет нужное поле JSON-вывода в `.md`/текст и передаёт следующему навыку (скрипты файлы не пишут) — рецепты в `docs/guru-family.md`.

## Безопасность секретов

Полная матрица бэкендов/хостов/схем/переменных — `references/backends-and-auth.md`. Критичные правила:

- **Basic vs Bearer по хостам.** `portal` (SWTR/SourceControl): основная схема — Basic. `sberworks` (Confluence/Jira): Basic **отклоняется сервером**, работает только PAT как `Bearer`.
- **Изоляция секретов.** Секрет одной системы никогда не уходит на хост другой. SWTR-секреты не переиспользуются для SourceControl (только с явным `SOURCE_CONTROL_REUSE_SWTR_AUTH=1`). `Confluence-PAT ≠ Jira-PAT ≠ SWTR-секрет` — токен одного приложения на другом даёт 401.
- **403 ≠ спецсимволы.** Пароли со спецсимволами (`} % # * …`) передаются корректно (покрыто `scripts/_test_swtr_env.py`), «экранирование» не предлагать никогда. На `portal` под 403 живут **три** разных отказа, и `scripts/guru_doctor.py` их различает: **шлюз авторизации** (HTML-страница «Ошибка при аутентификации», вердикт `stale_password`) — пароль не принят, чаще всего сменился доменный пароль, лечится обновлением `SWTR_BASIC_AUTH` через `scripts/guru_env_setup.py`; **ответ бэкенда на чтении** (JSON, вердикт `forbidden`) — Basic запрещён, вот тут предлагать PAT (`SWTR_BEARER_TOKEN` / `SWTR_AUTHORIZATION`, выпуск — https://portal.works.prod.sbt/ssd/privileges); **ответ бэкенда на записи** (JSON, вердикт `no_write_permission`) — кред принят, не хватает прав на запись в пространство, и PAT здесь не поможет: нужны права. Не советовать PAT на первый отказ: портал принимает Basic с паролем и запись под ним не блокирует.
- **Запись под Basic не запрещена.** POST на создание доходит до бэкенда и получает от него ответ — это проверяет write-зонд `guru_doctor.py` (бьёт в заведомо несуществующий space, поэтому ничего не создаёт). Отказ на создании задачи почти никогда не про схему авторизации: смотреть на `HTTP 570` (не заполнены обязательные поля) и на права в пространстве.
- **Env-файлы.** Скрипты читают секреты из окружения или `~/.swtr-review.env` (для sberworks дополнительно подгружается `~/.sberworks.env`). Файл сохранять в UTF-8. Никогда не просить вставить токен в текст задачи, не печатать его в отчет и не сохранять в файлы.
- При жалобах на авторизацию запускать `scripts/guru_doctor.py` (сценарий 16) — секрет не печатается.
- Если доступы не заполнены, доктор печатает `FIXABLE: <системы>` — по этой строке команда `/guru_doctor` предлагает заполнить `~/.swtr-review.env` автоматически: спрашивает логин и пароль, проверяет их, выпускает API-токен SourceControl и пишет файл через `scripts/guru_env_setup.py` (единственный скрипт навыка, который пишет в env-файл).

## Правила анализа качества

Проверять не только наличие заголовков, но и пригодность содержания для оценки и реализации. Для каждого существенного вывода указывать источник: поле заявки, раздел PRD, wiki-страница, локальный файл, SourceControl-файл или результат поиска.

Классифицировать замечания:

- `C` — критичный блокер: противоречие, отсутствие ключевой логики, невозможность оценить или реализовать без уточнения, риск нарушения безопасности или данных.
- `L` — логическая или архитектурная проблема: неоднозначный сценарий, слабая трассировка, неописанные переходы состояния, несовпадение API/данных/процессов.
- `D` — пробел документации: отсутствует полезная детализация, критерий приемки, нагрузочная оценка, владелец сопровождения, мониторинг, rollback или другое описание.

Для каждого замечания давать конкретное исправление, а не «уточнить» без указания, что должно появиться в документе.

Если требования/архитектурная постановка заявляют создание или изменение API, применять `references/api-requirements-checklist.md` к каждому методу: назначение, ограничения, rate limits, request/response-контракты, коды ошибок, алгоритм, гонки, corner cases, обработка ошибок. Отсутствие ограничений/rate limits должно быть явно зафиксировано, а не подразумеваться.

## Критерии готовности ответа

Перед завершением проверить, что результат:

- отвечает на конкретный сценарий пользователя, а не только запускает скрипты;
- для ревью документа — итоговый отчет сохранен в `docs/ai/<slug>/<YYYY-MM-DD>-review.md` агентом (не скриптом); для остальных сценариев результат — в ответе и stdout скриптов;
- для ревью содержит итоговую оценку готовности (`готово к разработке` / `нужны точечные уточнения` / `нужна существенная переработка` / `блокер для оценки`) и статистику замечаний по `C`, `L`, `D`;
- отделяет факты из источников от экспертных выводов;
- не содержит секретов, токенов и cookie;
- не содержит пустых заглушек, TODO без объяснения или непроверенных утверждений о коде.
