# PVM GURU

## Что умеет

Это единая точка доступа к рабочим задачам, документации и коду компании. Вы просите обычными словами — «что за задача», «найди похожие», «сколько таких задач», «проверь качество этой постановки», «как это сделано в коде», «покажи комментарии», «что закрыли за неделю» — а агент сам находит нужную задачу, страницу или фрагмент кода, показывает похожее, считает и фильтрует, проверяет качество постановки (PRD / CR / требований) и подсказывает, что доработать. Навык знает про две системы задач и две вики. По умолчанию он всегда работает с SWTR — задачами, вики и кодом на портале компании. Отдельные Jira и Confluence на `sberworks` он трогает только тогда, когда вы сами их назовёте («посмотри в жире», «страница Confluence») или дадите ссылку на `sberworks.ru`. Если вы назвали только номер задачи — например «дай инфу по PVM-52489» — он ищет в SWTR: такие номера бывают в обеих системах, и по одному номеру их не различить. Не нашёл — скажет об этом и спросит, идти ли в Jira. По вашей явной команде он может создавать задачи и оставлять комментарии, но по умолчанию только показывает и ничего не меняет. Ваши пароли и токены остаются только на вашем компьютере и никогда не попадают в ответы.

## Словарь терминов

| Термин | Что это |
|---|---|
| **SWTR** | Корпоративная система задач и вики на хосте `portal`. Основной источник задач и постановок. |
| **Юнит (unit)** | Любая карточка в SWTR: задача, требование, тест-кейс. Обозначается кодом вида `PVM-119134` или `CRPV-35498`. |
| **Space (пространство)** | Проект / раздел в трекере; задаёт префикс кода — `PVM`, `CRPV`, `TMS`. |
| **Wiki** | Вики-страницы с внутренней документацией, привязанные к задачам SWTR. |
| **SourceControl** | Корпоративное хранилище кода (репозитории), тоже на `portal`. По нему можно искать, как реализована функция. |
| **TMS** | Test Management System — часть SWTR для тестирования: тест-планы, циклы, кейсы, прогоны. |
| **PAT** | Personal Access Token — персональный токен доступа. Заменяет логин с паролем; для `sberworks` это единственный рабочий способ входа. |
| **Confluence / Jira sberworks** | Отдельные вики и трекер на хосте `sberworks.ru`. Это **не** SWTR — другие системы, у каждой свой отдельный PAT. Крайний приоритет: агент идёт туда только по вашему явному указанию. |

## Настройка за 5 минут

Всё, что нужно навыку — один файл с вашими доступами. Пароли и токены хранятся только у вас и никуда не отправляются, кроме самих корпоративных систем.

**Шаг 1. Решите, к каким системам нужен доступ.** Можно настроить не все сразу — заполните только нужные строки:

- SWTR (задачи + вики) и SourceControl (код) — на хосте `portal`;
- Confluence и Jira — на хосте `sberworks` (нужны, только если работаете с ними).

**Шаг 2. Получите доступы.**

- **SWTR (`portal`):** обычно достаточно вашего корпоративного логина и пароля (схема Basic). Если сервер запрещает вход по паролю (ошибка 403 при проверке ниже) — заведите персональный токен (PAT) в профиле системы.
- **SourceControl (`portal`):** логин тот же, а вместо пароля надёжнее использовать API-токен `sc_token` (именно он показан в примере ниже) — как его выпустить, см. [Cookbook SourceControl](https://portal.works.prod.sbt/ssd/tools/sc/convsupp/docs-ac21/src/branch/master/Cookbook_SourceControl.md#вариант-1-создание-полноценного-api-токена-через-python-скрипт). Подойдёт и корпоративный пароль, если сервер разрешает вход по паролю.
- **Confluence / Jira (`sberworks`):** только персональный токен (PAT). Вход по паролю там сервер отклоняет. Токен создаётся в профиле каждой системы: «Profile → Personal Access Tokens» (в Confluence и в Jira это **разные** токены — заведите по одному на каждую).

**Шаг 3. Создайте файл `~/.swtr-review.env`** в вашей домашней папке (на macOS это `/Users/<вы>/.swtr-review.env`, в Windows — `C:\Users\<вы>\.swtr-review.env`). Готовый шаблон со всеми переменными и комментариями, где выпускается каждый токен, лежит в каталоге скилла — `.env.example`, скопируйте его и заполните. Минимум — только нужные вам системы:

```
# SWTR Task Tracker + Wiki (portal)
SWTR_BASE_URL=https://portal.works.prod.sbt/swtr
SWTR_BASIC_AUTH=login_sbt:password_sbt

# SourceControl (portal) — отдельный кред (или тот же логин/пароль)
SOURCE_CONTROL_BASE_URL=https://portal.works.prod.sbt/ssd/tools/sc/api/v3
SOURCE_CONTROL_BASIC_AUTH=login_sbt:sc_token

# Confluence sberworks — только персональный токен (PAT)
CONFLUENCE_BASE_URL=https://sberworks.ru/wiki
CONFLUENCE_BEARER_TOKEN=<Confluence PAT>

# Jira sberworks — свой отдельный токен (PAT)
JIRA_BASE_URL=https://sberworks.ru/jira
JIRA_BEARER_TOKEN=<Jira PAT>
```

Ошибка 403 от `portal` чаще всего означает, что сменился доменный пароль, а в файле остался старый — обновите `SWTR_BASIC_AUTH`. Запустите `/guru_doctor`: он отличает отказ шлюза авторизации от отказа самого сервера и предложит обновить пароль. И только если доктор сказал, что Basic запрещает сам сервер **на чтении**, замените строку `SWTR_BASIC_AUTH=...` на `SWTR_BEARER_TOKEN=<ваш токен>` (и аналогично для `SOURCE_CONTROL_*`); токен портала выпускается на https://portal.works.prod.sbt/ssd/privileges и принимается обеими портальными системами (страница **скачивает файл** `privileges` — открыть его, пролистать до строки `[Authorization] header: Bearer` и скопировать токен после неё **без слова `Bearer`**). Токен годится и как основной способ входа, если надоело обновлять пароль после каждой смены: если заданы обе схемы, побеждает `SWTR_BASIC_AUTH`, так что для перехода на токен уберите её из файла. Если 403 приходит на создании задачи, а чтение работает — это не про схему входа, а про права в пространстве: токен не поможет, нужно запросить доступ.

На macOS / Linux этот же файл можно создать одной командой:

```bash
cat > ~/.swtr-review.env <<'ENV'
SWTR_BASE_URL=https://portal.works.prod.sbt/swtr
SWTR_BASIC_AUTH=login_sbt:password_sbt
ENV
chmod 600 ~/.swtr-review.env
```

> **Про кодировку файла (важно для Windows).** Сохраняйте `~/.swtr-review.env` в кодировке **UTF-8 без BOM** (в «Блокноте»: «Файл» → «Сохранить как» → в списке кодировок выбрать «UTF-8»). Не выбирайте «Юникод» / UTF-16. BOM и UTF-16 теперь распознаются автоматически, но UTF-8 без BOM — самый надёжный вариант. Пароль со спецсимволами (`} % # * & $ !` и пробелы) экранировать не нужно — символы внутри кавычек сохраняются как есть.

## Проверка доступа: `/guru_doctor`

> Команда `/guru_doctor` (как и другие команды скилла) появляется в агенте только после bootstrap-шага `node ~/.agents/skills/pvm-guru/install.mjs` — запустите его один раз вслед за `npx skills add`/`update`. Субагентов (`executor`, `fixer`, …) тот же шаг раскладывает в OpenCode и GigaCode (во второй — с конвертацией формата) — в Claude Code и Codex их нет и после bootstrap-шага. И клиент после установки нужно перезапустить: команды он читает при старте. Подробности и почему — в README репозитория, раздел «Установка».

Это первое, что стоит запустить после настройки, и первое, что стоит запустить, если скилл вдруг перестал работать. Диагностика **не печатает** ваш пароль или токен — показывает только «отпечаток» доступа (длину и классы символов), выбранную схему входа, состояние TLS и HTTP-статус ответа сервера.

Проще всего — командой прямо в агенте:

```text
/guru_doctor
```

Или скриптом. `$SKILL_DIR` в примерах — каталог этого скилла: после `npx skills add … -g` это `~/.agents/skills/pvm-guru`, в чекауте репозитория — `.gigacode/skills/pvm-guru`; задайте его один раз (`SKILL_DIR=~/.agents/skills/pvm-guru`). Без `--system` проверяются все четыре системы за один запуск, а в конце печатается итоговая строка `SUMMARY`:

```bash
# все 4 системы сразу + SUMMARY
python3 $SKILL_DIR/scripts/guru_doctor.py

# по одной системе
python3 $SKILL_DIR/scripts/guru_doctor.py --system task_tracker
python3 $SKILL_DIR/scripts/guru_doctor.py --system source_control
python3 $SKILL_DIR/scripts/guru_doctor.py --system confluence
python3 $SKILL_DIR/scripts/guru_doctor.py --system jira

# только конфигурация, без обращения к серверам
python3 $SKILL_DIR/scripts/guru_doctor.py --no-network
```

Как читать вердикт:

- **200** — доступ работает, всё настроено верно. Для Confluence и Jira дополнительно проверяется, что определилась ваша личность: там анонимный доступ тоже отвечает `200`, поэтому одного кода мало.
- **401** — доступ неверный: опечатка в логине / пароле или неправильный токен. Для `sberworks` проверьте, что это токен именно этой системы (токен Confluence не подходит для Jira и наоборот).
- **403** — доступ сформирован правильно, но сервер запрещает вход по паролю. Перейдите на персональный токен (см. таблицу ниже). Дело **не** в спецсимволах пароля — их экранировать не нужно.
- **404** (у портала) — цель пробника не видна вашей учётной записи. Это **не** вердикт про авторизацию: задайте свою цель через `SWTR_PROBE_UNIT`, `SOURCE_CONTROL_PROBE_TENANT` / `SOURCE_CONTROL_PROBE_PROJECT` или `--probe-path`.
- **network/TLS error** — сервер недоступен или сертификат не доверен: проверьте сеть и VPN.
- **no credential** — для этой системы переменные не заданы: заполните нужные строки в `~/.swtr-review.env`.

Диагностика также печатает путь к вашему `~/.swtr-review.env` и его кодировку: если файл сохранён в UTF-16, она прямо предупредит, что нужен UTF-8.

Последним идёт блок `profile state` — состояние профиля умолчаний: есть файл или нет, путь к нему, когда он сохранён, заполнены ли логин и основное пространство. Сам логин диагностика не печатает. На строку `SUMMARY` и код возврата блок не влияет: без профиля скрипты работают как раньше, поэтому это отдельный диагноз, а не проблема доступа. В режиме одной системы (`--system`) блок не печатается, с `--no-network` — печатается: это локальный файл.

Коды возврата (пригодятся в скриптах): `0` — всё в порядке, `1` — есть проблемы. В режиме одной системы (`--system`) дополнительно: `2` — нет креда, `3` — запрещено (403), `4` — сеть или TLS.

## С чего начать: `/guru-start`

Если вы только что поставили GURU, запустите `/guru-start`. Команда посмотрит, что
у вас установлено и работают ли доступы, спросит вашу производственную роль и
покажет, чем набор навыков полезен именно в ней — а в конце предложит прогнать
один сценарий на ваших собственных задачах.

Отдельным шагом команда собирает **умолчания**: логин, основное пространство и
пространства в поле зрения, тип задачи, проект и tenant SourceControl. Варианты
ответов она предлагает по вашим же данным — пространствам, в которых на вас есть
задачи. Вопросов не больше четырёх, любой можно пропустить, и от шага целиком
можно отказаться одним «не надо».

Ничего в корпоративные системы при этом не записывается: онбординг только читает.
Единственная запись — локальная и по вашему согласию: собранные умолчания
сохраняются в файл `~/.config/pvm-guru/profile.json` на этой машине.

Порядок после установки: `node ~/.agents/skills/pvm-guru/install.mjs` →
перезапуск клиента → `/guru_doctor` → `/guru-start`.

## Ваши умолчания: `/guru_profile`

Профиль — то, что навык помнит про вас между запусками: логин в трекере, роль,
основное пространство и пространства в поле зрения, тип задачи, продукт и
компоненты, tenant, проект и репозитории SourceControl, ключ проекта Jira и
пространство Confluence. Когда значение не названо в запросе, скрипты берут его
отсюда: «что на мне» и «найди похожие» перестают требовать `--space` и `--user`
каждый раз.

Порядок источников — **явное → окружение → профиль**: названное в запросе всегда
сильнее сохранённого, а если пусто и в профиле, всё работает ровно как раньше.
Что именно подставилось и откуда, скрипт печатает в поле `defaults_applied`.
Разово выключить умолчания — фраза «найди везде» (в командах это флаг
`--no-profile`).

Команда `/guru_profile` показывает карту умолчаний и правит её одной фразой:
«сделай основным пространством CRPV», «запомни мой логин», «убери продукт»,
«сбрось профиль» (файл удаляется только после явного «да»). Секретов в профиле
не бывает: пароли и токены живут в `~/.swtr-review.env` и настраиваются через
`/guru_doctor`, а ключ, чьё имя похоже на секрет, скрипт на записи отклоняет.
Подробности — сценарий 25 в `references/usage-scenarios.md`.

## Если что-то не работает

| Симптом | Что это значит | Что сделать |
|---|---|---|
| `SWTR authorization is not configured` (или аналог) | Файл с доступами не подхватился | Проверьте путь `~/.swtr-review.env`, имена переменных и кодировку файла (см. про UTF-8 ниже) |
| **HTTP 401** | Логин / пароль / токен неверны | Исправьте опечатку. Для `sberworks` — токен Confluence ≠ токен Jira, нужен свой на каждую систему |
| **HTTP 403** от `portal` | Пароль доходит до сервера правильно (это НЕ про спецсимволы). Чаще всего его не принял шлюз авторизации — сменился доменный пароль, а в файле остался старый | Запустите `/guru_doctor` — он различает три случая и предложит обновить пароль. Не подставляйте старый пароль повторно: несколько неудач блокируют доменную учётку. Экранировать пароль не нужно |
| **HTTP 403**, доктор сказал «credential well-formed but forbidden» | Ответил сам сервер на **чтении**: Basic-вход запрещён | Замените `SWTR_BASIC_AUTH=...` на `SWTR_BEARER_TOKEN=<токен>` (персональный токен) |
| **HTTP 403** при создании задачи, доктор сказал «refuses the write itself» | Кред принят, не хватает прав на запись в это пространство | Запросите права в пространстве. Персональный токен здесь не поможет — дело не в схеме входа |
| Задача не создаётся, **HTTP 570** | Не заполнены обязательные поля space | Скрипт подставляет `workflow_status` сам и печатает `hint` с именем недостающего поля — добавьте его через `--attribute key=value` |
| Файл не читается / «кракозябры» / игнорируется | Файл сохранён в неверной кодировке | Пересохраните `~/.swtr-review.env` в **UTF-8 без BOM** (в «Блокноте»: «Сохранить как» → «UTF-8», не «Юникод») |
| `UnicodeEncodeError` в самом скрипте (Windows) | Это про кодировку **вывода**, а не про `~/.swtr-review.env`: Windows кодирует перенаправленный stdout страницей `cp1251`, и символ вне неё обрывает печать | Обновите скилл: скрипты переключают вывод на UTF-8 сами, а `guru_doctor.py` печатает только ASCII |
| `SWTR_TOKEN` задан, но ответ **401** | Раньше токен уходил в заголовок без схемы (`Authorization: <токен>`) | Обновите скилл — теперь он оборачивается в `Bearer`. На старой версии используйте `SWTR_BEARER_TOKEN` |

Полная таблица систем, хостов и переменных — в `references/backends-and-auth.md`.
