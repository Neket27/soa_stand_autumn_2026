# Anti-patterns

## Deprecated API / паттерны
- **Повтор `POST /payments` без Idempotency-Key** — не использовать. Любой повтор (500, тайм-аут, «пробую ещё раз») рискует двойным списанием. Вместо: стабильный ключ на заказ + реконсиляция через `GET /payments?order_id=`. Причина: наивный пример (orders/main.go, `charge()`/`chargeOnce()`) именно так проваливает S2 и S5.
- **Синхронное ожидание Payment в пути запроса `POST /orders`** (тайм-аут > 1 с) — не использовать. Вместо: быстрое решение в рамках бюджета + `pending` и фоновая обработка. Причина: S3 (ответ Payment через 2 с) и S4 (висение соединения) гарантированно ломают бюджет 1 с.
- **Считать сетевую ошибку/тайм-аут «деньги не списаны»** — не использовать. Ответ может потеряться после выполнения операции (S5). Вместо: после неопределённого исхода — реконсиляция через `GET /payments?order_id=`.
- **5xx на `POST /orders`** при любой недоступности Payment/Inventory — не использовать. Вместо: `201` + `pending`. Причина: раннер считает 5xx ошибкой; уровень «засчитано» требует их отсутствия.
- **Плотный повтор/полинг Payment во время блэк-хола** — не использовать. Вместо: backoff/паузы и учёт бюджета запросов. Причина: S4 лимитирует число запросов к Payment за время отказа (открыто: 30).

## На чем спотыкаются
- Забывают, что **`GET /payments` тоже входит в бюджет S4** во время блэк-хола (downRequests в runner/checks.go считает и POST, и GET).
- Подгоняют решение под открытые числа `runner/params/task1.json` (доли, задержки, 30 с паузы, 30 запросов) — на проверке параметры другие.
- Оставляют `pending` в конце прогона: фоновая обработка обязана уложиться в паузу раннера (открыто 30 с, на проверке — другое значение).
- Забывают снять резерв при 402 → проверка «rejected: резерв снят» падает.
- Генерируют `id` заказа, отличный от `order_id`, который уходит в Payment/Inventory, — раннер не сможет свести факты.
- МЕНЯЮТ файл вне `orders/` (хоть README) — задание проваливается автоматически.
- Создают symlink в `orders/` — запрещено CI везде.
- Доверяют 201 от `POST /payments` без сохранения факта: ответ может не дойти (S5), истину даёт только факт списания.
- Запускают `make scenarios` во время прогона из дашборда — оба прогона портят результат друг друга.

## Bad example
`orders/main.go` (текущий наивный пример) — три конкретных бага:
1. `charge()` → `chargeOnce()` дважды без Idempotency-Key: повтор после 500/тайм-аута = риск двойного списания;
2. `call()` — HTTP без тайм-аутов: медленный/зависший Payment держит запрос `POST /orders` (бюджет 1 с);
3. `fail()` — отвечает 5xx при любой ошибке Payment/Inventory вместо `201 pending`.

Этот файл — легитимная отправная точка: либо чинить именно эти места, либо писать сервис с нуля.
