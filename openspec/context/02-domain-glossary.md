# Глоссарий

## Компоненты стенда
- **Стенд (stand)** — docker-compose окружение: `postgres` + `mocks` (заглушки) + `orders` (ваш сервис) + `runner` (проверка) + опциональные `runner-ui`, `docs`.
- **Orders** — сервис оформления заказов, который вы пишете. Единственный изменяемый компонент.
- **Payment** — заглушка платёжного сервиса: списание денег (`POST /payments`), поиск списаний по заказу (`GET /payments?order_id=`).
- **Inventory** — заглушка склада: резервирование товара (`POST /reservations`), снятие резерва (`DELETE /reservations/{order_id}`), статус резерва (`GET /reservations?order_id=`).
- **Раннер (runner)** — программа-проверяльщик: сценарии S1–S5, поток заказов, журнал фактов, отчёт PASS/FAIL.
- **Заглушки (mocks)** — реализации Payment и Inventory со встроенными режимами отказов.
- **Дашборд** — веб-интерфейс заглушек (`make ui`): режимы отказов, ручные заказы, прогон сценариев.

## Домен заказов
- **Заказ (order)** — заявка покупателя: `user_id`, позиции (sku, qty, price_cents). Идентификатор заказа генерирует **Orders**.
- **order_id** — id заказа; **тот же** идентификатор Orders передаёт в Payment и Inventory. По нему раннер сводит факты заглушек с заказами.
- **amount_cents** — сумма заказа = `Σ qty × price_cents`; ровно столько списывается в Payment.
- **Статусы заказа** (в ответе `POST /orders` и `GET /orders/{id}`):
  - `paid` — товар зарезервирован, деньги списаны один раз;
  - `rejected` — заказ не состоялся: денег не взяли, резерва нет;
  - `pending` — исход ещё неизвестен, Orders завершает обработку в фоне (допустимый ответ на POST).
- **Резерв (reservation)** — бронь товара в Inventory на `order_id`; статусы `held` / `released`. Повторный `POST /reservations` с тем же `order_id` идемпотентен (200), `DELETE` идемпотентен (204).
- **Списание (charge)** — факт списания денег в Payment: `charge_id`, `order_id`, `amount_cents`, `status: captured`.
- **Idempotency-Key** — заголовок `POST /payments`, выбирает клиент: первый успешный запрос с ключом выполняет списание (201); повтор с тем же ключом **и тем же телом** возвращает ту же операцию (200, тот же `charge_id`, или снова 402) без нового списания; тот же ключ с **другим** телом — 422; одновременные запросы с одним ключом обрабатываются по очереди.
- **402 (declined)** — банк отклонил оплату: деньги не списаны.

## Отказы Payment
- **500** — внутренняя ошибка Payment: операция **не выполняется**, деньги не списаны.
- **Блэк-хол (blackhole)** — Payment не отвечает вообще: соединение висит (сценарий S4).
- **Потерянный ответ (lost response)** — операция **выполнена**, но соединение рвётся без ответа (сценарий S5). По факту это «деньги списаны, а клиент не знает».
- **Задержка (latency)** — ответ приходит с искусственной задержкой (S3: 2 с).

## Проверка и сдача
- **S1–S5** — сценарии задания 1 (см. 01-product-context.md).
- **Журнал фактов** — записи заглушек о всех запросах, списаниях, резервах и отказах; раннер сверяет его с финальными статусами заказов.
- **Бюджет (budget_ms)** — лимит времени ответа на `POST /orders`; открыто 1000 мс.
- **WAIT (wait_s)** — пауза раннера после последнего заказа, пока сервис доводит фоновую обработку; открыто 30 с.
- **Открытые параметры** — `runner/params/task1.json`, видны студенту. **Закрытые параметры** — те же сценарии с другими числами, используются на проверке; их значения неизвестны.
- **Уровень «засчитано» / «полностью»** — критерии успешности задания (см. 01).
- **ИСУ** — номер задачи студента; заголовок PR: `ИСУ <номер>`.
- **check `task_1`** — вердикт CI в PR.
