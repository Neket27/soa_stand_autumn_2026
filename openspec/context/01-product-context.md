# Product Context

## Что за продукт [🟢 Абсолютно уверен (≈100-80%)]
Учебный стенд курса «Архитектура микросервисов и SOA — осень 2026» (исходный репозиторий `ippaveln/soa_stand_autumn_2026`). В стенде уже есть: PostgreSQL 16, заглушки (mocks) сервисов Payment и Inventory и раннер сценариев, который проверяет систему **как чёрный ящик** — только по свойствам: сколько раз списаны деньги, какой итоговый статус заказа, уложился ли ответ на `POST /orders` в 1 секунду. Язык и внутреннее устройство сервиса раннер не видит.

Вы пишете ровно один сервис — **Orders** — в каталоге `orders/`. Курс допускает любой язык; выбран Java (ADR-001).

## Пользователи и роли
- **Студент (вы)** — разрабатывает Orders, сдаёт PR, защищает решение устно (5–10 минут, вопросы «что будет, если упасть в этой строке»).
- **Раннер** — чёрный ящик: шлёт потоки заказов `POST /orders`, ждёт, затем сверяет статусы (`GET /orders/{id}`) с журналом фактов заглушек.
- **Mock-дашборд** (`make ui`) — ручной способ ставить режимы отказов и отправлять заказы; нужен для отладки.
- **CI курса (workflow `soa-grade`)** — официальная проверка PR: diff файлов, сборка `orders/Dockerfile`, прогон сценариев.

## Ключевые сценарии (задание 1)
Поток заказов при отказах Payment. Каждый сценарий: раннер шлёт N заказов с заданным темпом, ждёт `WAIT` (открыто: 30 с), проверяет итог.

| № | Поведение Payment | Что проверяется |
|---|---|---|
| S1 | Работает, ~10 % оплат банк отклоняет (402) | paid — ровно одно списание; rejected — без списания и со снятым резервом |
| S2 | ~1/3 запросов отвечает 500 (операция не выполняется) | ≤ 1 списания на заказ; в итоге оплачено ≥ 90 % |
| S3 | Операция выполняется, но ответ через 2 с | каждый ответ на POST ≤ 1 с; в итоге paid или rejected без денег |
| S4 | Не отвечает 60 с (соединение висит), потом восстанавливается | POST ≤ 1 с; за время отказа ≤ 30 запросов к Payment; заказы после восстановления оплачены |
| S5 | Операция выполнена, ответ потерян (соединение рвётся без ответа) | ≤ 1 списания на заказ; каждый заказ с деньгами в итоге paid |

Везде дополнительно: ни одного заказа с двумя списаниями; ни одного `rejected`, за который списаны деньги; ни одного 5xx на `POST /orders`.

## Уровни
- **«Засчитано»**: S1 PASS + во всех сценариях нет двойных списаний + все ответы на POST ≤ 1 с. `pending` в конце допустимы.
- **«Полностью»**: все пять сценариев PASS, в конце нет `pending`, нет списаний без `paid`.

## Что нельзя ломать [🟢 Абсолютно уверен (≈100-80%)]
1. Ни один заказ не оплачен дважды (двойное списание — провал проверки).
2. Если деньги списаны — заказ в итоге `paid`.
3. `rejected` — деньги не взяты и резерв товара снят.
4. Ответ на `POST /orders` — не позже 1 секунды при любом поведении Payment; `5xx` запрещены (`400` — только на некорректное тело).
5. Пока Payment недоступен — не перегружать его запросами (бюджет S4).
6. После восстановления Payment заказы снова оплачиваются.
7. Файловая политика: отличиться от baseline может только `orders/` (+ `.gitignore`).

## Known limitations
- Параметры проверки **закрытые**: на ней другие доли ошибок, задержки и моменты отказа; решение, подобранное под открытые числа, не пройдёт (README, «Как сдавать»).
- База — в памяти (tmpfs): `make up` / `make scenarios` пересоздают её, каждый прогон начинается с пустой базы; схему создаёт сам сервис при старте.
- `make grade` требует Go 1.26 (на dev-машине Go нет) — локально использовать `make scenarios`.
- Прогон из дашборда и `make scenarios` конфликтуют (одни заглушки) — не запускать одновременно.
- Остальной стенд (mocks/, runner/, examples/, cmd/) — на Go, read-only.
