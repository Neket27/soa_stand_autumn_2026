# Change: fix-circuit-breaker-probe

## Why

Circuit breaker может застыть навсегда в состоянии HALF_OPEN. Из HALF_OPEN система
выходит только через `onSuccess()` или `onTimeoutOrConnError()`, а `OrderProcessor`
вызывает их только при исходах `CHARGED` и `NETWORK`. Если пробный заказ — единственный
запрос, который HALF_OPEN пропускает (`PaymentCircuitBreaker.allow()`,
orders/src/main/java/orders/flow/PaymentCircuitBreaker.java:30-32) — получает `402`
или `500`, ни один вызов к брейкеру не совершается: состояние не меняется, `allow()`
всегда `false`, все воркеры спят по кругу, все оставшиеся заказы `pending` до конца
прогона.

В открытых параметрах сценариев S4 нет `decline_rate`/`fail_rate`
(runner/params/task1.json), поэтому баг на локальном прогоне не виден. Проверка идёт с
другими долями ошибок: 402/500 на пробном запросе — реалистичный исход.

Сопутствующие проблемы, найденные при разборе:

1. Код не выполняет требование из основной спеки «first network failure opens the
   breaker early»: `onTimeoutOrConnError()` вызывается после реконсиляционного GET
   (orders/src/main/java/orders/flow/OrderProcessor.java:118-128), который в блэк-холе
   сам висит ~1 с — брейкер открывается через ~2 с вместо требуемых ~1 с.
2. `PaymentClient.hasCharges(): boolean` возвращает `false` и при пустом списке, и при
   сетевой ошибке — «проверено: заряда нет» и «проверить не удалось» conflated. В
   матрице отказов стенда это безопасно (в блэк-холе операция гарантированно не
   выполняется — mocks/payment.go:29-40), но опора — на семантику заглушки, а не на
   структуру кода.
3. Окно брейкера (30 с) сравнимо с паузой раннера: если конец блэк-хола «не совпал» с
   окном проба, хвост заказов ждёт восстановления до ~30 с после recovery — при
   проверочной паузе, отличной от открытой 30 с, это риск провала «заказы после
   восстановления оплачены».

## What changes

### 1. Детерминированные исходы проба (P0)

- Новая семантика брейкера: **любой HTTP-ответ Payment (200/201/402/500) — доказательство
  доступности** → `onReachable()` (HALF_OPEN → CLOSED); **только NETWORK** (тайм-аут,
  обрыв соединения) → `onUnavailable()` (→ OPEN).
- Переименование `onSuccess()` → `onReachable()`, `onTimeoutOrConnError()` →
  `onUnavailable()`: имя отражает семантику (был ответ / не было ответа), а не «успех».
- Watchdog для HALF_OPEN: если исход проба не доложен за `CIRCUIT_BREAKER.PROBE_WINDOW_MS`
  (по умолчанию 10 с), брейкер возвращается в OPEN. Защита от смерти пробного воркера
  без доклада (непойманное исключение в цикле воркера после того, как `allow()` выпустил
  проб).

### 2. Брейкер открывается в момент тайм-аута charge

В ветке `NETWORK` `onUnavailable()` вызывается сразу после тайм-аута списания,
**до** реконсиляционного GET. Сценарий спеки «OPEN within that same second» становится
правдой в коде, а не только в спеке. Бюджет запросов не растёт (по-прежнему ограничен
размером пула воркеров).

### 3. Трёхсостоянная реконсиляция

- `PaymentClient.hasCharges(): boolean` → `PaymentClient.reconcile():
  ReconciliationResult { CHARGED, NOT_CHARGED, UNKNOWN }`:
  200 + непустой список → `CHARGED`; 200 + пустой список → `NOT_CHARGED`;
  ошибка / тайм-аут / не-200 → `UNKNOWN`.
- В ветке NETWORK: `CHARGED` → `paid`; `NOT_CHARGED` → `release` + `rejected`;
  `UNKNOWN` → заказ остаётся `pending` (без reject — деньги могли списаться),
  брейкер уже OPEN, reaper подхватит заказ после восстановления.
- Побочный эффект в плюс: в S4 заказы, созданные во время блэк-хола, станут `paid`
  после восстановления вместо `rejected` — требование «после восстановления заказы
  снова оплачиваются» выполняется в самой строгой интерпретации.

### 4. Окно брейкера 30 с → 15 с

- `CIRCUIT_BREAKER.OPEN_FOR_MS`: 30000 → 15000 (явно в `application.properties`).
- Худший случай «конец блэк-хола → первый успешный проб» ≤ openForMs + время проба;
  с 30 с этот хвост может превысить проверочную паузу раннера. Цена: пробы в блэк-холе
  ~2 запроса за окно; для открытого S4 (60 с) суммарно ≤ ~22 запроса при лимите 30
  (формула и расчёт — в design.md, D4).

- Соответствующие тесты (`PaymentCircuitBreakerTest`, `OrderProcessorTest`,
  `PaymentClientTest`)

## Non-goals

- Не менять синхронный путь (`reserve` в рамках бюджета), Idempotency-Key, тела запросов.
- Не вводить счётный брейкер (открытие после N непрерывных сбоев): спека требует
  «открыть при первом сетевом сбое».
- Не пропускать реконсиляционный GET для пробов при открытом брейкере (упрощение
  бюджета) — S5-семантика (charge выполнен, ответ потерян) требует быстрого GET.
- Не менять дедлайн воркера (25 с), период reaper (500 мс), размер пула (8).
- Разрез OrderProcessor и перенос ответственности — отдельный change
  `2026-10-08-refactor-order-flow`.
- Изменения вне `orders/`.
