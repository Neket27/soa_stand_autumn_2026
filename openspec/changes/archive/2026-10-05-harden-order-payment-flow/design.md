# Design: harden-order-payment-flow

Опирается на инварианты 03-architecture.md (№2 — бюджет 1 с, №3 — ≤ 1 списания, №4 — деньги
⇒ paid, №5 — rejected чистый, №6 — не перегружать Payment при отказе) и ADR-001 (Java 21,
Spring Boot, фоновый пул воркеров).

## D1. Single-flight обработка заказов (гонка inFlight)

### Проблема

`BackgroundWorker` хранит метку обрабатываемых заказов в `ConcurrentHashMap inFlight`, но:

- `workerLoop` делает `inFlight.put(orderId, TRUE)` **после** `queue.take()` — неатомарно
  относительно постановки в очередь;
- `reaper` делает `putIfAbsent` **до** `queue.offer` — т.е. сам ставит метку «кто-то
  обрабатывает», хотя обрабатывать ещё никто не начал.

Результат: контроллер ставит заказ X в очередь; reaper видит X `pending` в БД, не в inFlight
(воркер ещё не взял) — и ставит X второй раз. Два воркера берут X и обрабатывают параллельно:
лишние запросы к Payment, двойные `transition` в БД. Двойное списание при этом исключено
(Idempotency-Key), но при блэк-холе каждый дубль = +2–3 запроса к лимиту S4.

### Решение

Метку устанавливает только воркер, в момент начала обработки, атомарно:

```java
// workerLoop
String orderId = queue.take();
if (inFlight.putIfAbsent(orderId, Boolean.TRUE) == null) {
    try {
        orderProcessor.processUntilTerminal(orderId, ..., MAX_DEADLINE);
    } finally {
        inFlight.remove(orderId);
    }
} // иначе: другой воркер уже обрабатывает — дубль отбрасываем
```

Reaper перестаёт ставить метку, только читает:

```java
for (String orderId : orderRepository.findPendingIds()) {
    if (!inFlight.containsKey(orderId)) {
        queue.offer(orderId);
    }
}
```

Остаточный race (reaper проверил `containsKey=false`, одновременно воркер забрал заказ)
безвреден: появится дубликатная копия в очереди, второй воркер отбросит её по `putIfAbsent`.
Ограничение: обработка одного заказа живёт не дольше `MAX_DEADLINE` (25 с), после чего метка
сбрасывается и reaper снова подхватит заказ, если он ещё `pending`.

## D2. Убрать pre-charge reconciliation GET

### Проблема

Текущий раунд `processUntilTerminal` для «свежего» заказа: `hasCharges` (GET) → `charge`
(POST) → при NETWORK ещё `hasCharges` (GET). Три запроса к Payment, и:

1. при блэк-холе каждый такой заказ шлёт 3 запроса в лимит S4 (наблюдено: 21 из 30);
2. pre-charge GET занимает первую секунду раунда — первый NETWORK (открытие брейкера)
   наступает на ~3-й секунде сценария, за это время в CLOSED-состоянии успевают начать
   обработку ещё ~5 заказов (каждый со своими 3 запросами);
3. проверка избыточна: заказу, у которого списание уже выполнено, идемпотентный
   `POST /payments` (тот же `Idempotency-Key` и тело) вернёт `200` для того же списания —
   это тот же исход, что находил pre-charge GET.

### Решение

Из раунда убрать pre-charge `hasCharges`. Новый раунд:

```
allow() (гейт брейкера)
  → charge (POST, 1 с, Idempotency-Key = order_id)
      CHARGED (200|201)   → onSuccess → transition paid
      DECLINED (402)      → release → transition rejected
      SERVER_ERROR (500)  → один повтор POST (операция не выполнялась)
      NETWORK (таймаут/потеря) → hasCharges (GET):
          нашёл           → onSuccess → transition paid
          не нашёл        → onTimeoutOrConnError → release → transition rejected
```

Реконсилирующий GET остаётся ровно там, где он обязателен по инварианту №3 («нет ответа» ≠
«деньги не списаны») — после неопределённого исхода. Факты заглушек, на которых держится
безопасность (03-architecture.md, «Важные детали заглушек»):

- `500` — операция гарантированно не выполнена → повтор POST безопасен;
- lost response / таймаут — операция либо не выполнялась (блэк-хол: заглушка не выполняет
  операцию во время блэк-хола, соединение просто висит), либо выполнена и записана в
  `charges` до ответа/потери → `hasCharges` её находит;
- `200` на повторный POST с тем же ключом и телом — та же операция, новое списание не
  выполняется.

Побочный эффект на блэк-холе (S4): первый NETWORK известен на ~1-й секунде (только POST),
а не на ~3-й. Брейкер открывается на ~2 с раньше → в CLOSED-состоянии проходит ~2–3 заказа
вместо ~7. Оценка запросов за 60 с блэк-хола (8 воркеров, темп 2/с): залп 2–3 заказа ×
2 запроса + 1 зонд-раунд × 2 ≈ **6–8** против 21 наблюдаемых; худший случай (все 8 воркеров
в залпе) ≈ 16 + зонды по 2 на каждые 30 с окна.

### Отказ от альтернатив

- **Держать pre-charge GET «на всякий случай»** — отклонено: платим им 21/30 на открытом
  прогоне, а при скрытых параметрах (длиннее отказ, быстрее темп) запас тает.
- **Отказаться от POST-first и решать исход только по GET** — отклонено: GET не создаёт
  факта; POST с ключом — единственная операция, которая и списывает, и подтверждает.

## D3. Мёртвая ветвь "PAID" в контроллере

`processOnce` возвращает только `REJECTED` (резерв не взят) или `PENDING` (резерв взят,
исход — фоновым). Ветвь `if ("PAID".equals(result))` в `createOrder` недостижима — удалить,
чтобы контракт возвращаемых значений `processOnce` не расползался.

## D4. Рассматривалось и отклонено

- **GET-зонд в HALF_OPEN** (вместо полного раунда воркера): переход OPEN→HALF_OPEN
  обрабатывался бы одним `GET /payments?order_id=...` — зонд стоит 1 запрос вместо 2,
  но (а) требует выделенного order_id «проба», который попадёт в журнал фактов и на
  дашборд, (б) усложняет брейкер (отдельный путь зонда, который не связан с реальным
  заказом), (в) выигрыш — 1 запрос на 30 с окна, при текущей оценке 6–8 запросов за всё
  окно это не меняет порядок. Отклонено: сложность не окупается.
- **Сократить OPEN_FOR_MS (30 с → 10 с)** — отклонено: восстановление после отказа
  ускорится, но зондов в длинном блэк-холе станет в 3 раза больше (по раунду на окно),
  что съедает выигранный в D2 запас по лимиту S4.
- **Адаптивный backoff брейкера** (дольше открыт — реже зонды) — отклонено: детерминированное
  30-с окно проще объяснить на защите и предсказать при любых параметрах.

## Обязательные ответы

**Как соблюдается бюджет 1 с.** Не изменено: синхронный путь `POST /orders` — вставка
`pending` в БД + резерв в Inventory (тайм-аут 890 мс, Inventory в задании 1 не отказывает);
в синхронном пути обращений к Payment нет вообще. Ответ — `201 pending` до ~100 мс.

**Как исключено двойное списание.** Не изменено, усилено: каждый `POST /payments` несёт
`Idempotency-Key: order_id` с неизменным телом (сумма из БД), заглушка по ключу возвращает
первую же операцию (`200`) и новое списание не выполняет; статусные переходы в БД — только
из `pending` (`UPDATE ... WHERE status='pending'`), победитель один. D1 дополнительно
убирает параллельную обработку одного заказа, которая раньше могла давать два одновременных
POST (безопасных по ключу, но лишних).

**Как заказ с потерянным ответом становится paid.** Ответ потерян → `NETWORK` →
`hasCharges` (заглушка записывает списание до ответа/потери, GET в задании 1 не
отказывается вне блэк-хола) → нашёл → `paid`. Если раунд оборвался по дедлайну до решения —
reaper повторно ставит заказ в очередь; следующий раунд шлёт POST с тем же ключом,
заглушка отвечает `200` (списание уже записано) → `paid`. В блэк-холе ответа теряется быть
не может — операция во время блэк-хола не выполняется, заказ честно `rejected` без денег
и со снятым резервом (инвариант №5).

**Как ограничивается нагрузка на Payment в блэк-холе.** Первый NETWORK (POST, 1 с)
открывает брейкер на ~1-й секунде (D2); пока OPEN (30 с) воркеры не шлют ни одного запроса,
reaper не подхватывает `pending`. В HALF_OPEN проходит ровно один раунд-зонд (2 запроса);
успех закрывает брейкер, неудача — открывает снова. Оценка для 60 с окна: 6–8 запросов
(наблюдалось 21 до изменений); верхняя оценка — 2 на каждые 30 с окна + залп не более
8 воркеров × 2 = 16.
